# ENet 玩家主机联机实施顺序

日期：2026-10-28。
状态：推荐执行计划；本次仅创建任务文档，未开始修改代码。

## 范围

先实现 Unity 玩家主机 + ENet 本机多进程；不引入 Realm、DS Agent 或独立 DS 部署。保留纯 C# 战斗核心方向。使用 GameClient/GameServer 命名，不额外增加 Session 包装。沿用现有主机定序、各端模拟方向；ENet 仅负责传输。

## 1. 统一输入和本地身份

- 引入最小 GameClient 提交入口与 GameServer 权威入口，先用进程内消息传递，不接网络。
- BattlePresenter 和 W 键输入改走该入口，不能直接操作权威队列。
- 建立 LocalPlayerContext；由本地测试配置提供玩家，后续由握手分配，不依赖 Presenter 序列化 playerIndex 或写死 player0。
- Q 进入战斗迁至主机流程；S 直接抽牌限制为显式调试功能，纯客户端不能直接调用。
- 请求 Id 与权威 CommandId 分离；最小回应可先本地实现确认、拒绝与终态。

验收：单进程现有出牌可用；主机输入仍被权威规则拒绝；Presenter 不再直接调用 BattleCommandManager.Enqueue/Submit，待处理请求由其回应结束等待。

## 2. 抽离战斗核心的 Unity 依赖

- CardDefinitionManager 的 Sprite/Resources.Load 拆入客户端视觉目录。
- GameState/StateManager 不接收 MonoBehaviour，不决定 Application 路径；路径、日志、记录 sink 从入口注入。
- ActionExecutor 改为可外部推进的纯 C# 执行；规则不依赖动画完成；不因 IEnumerator 是现有签名就强制重写所有 Action。
- HandCardChooseAction 改显式等待状态，保留 ChoiceId/ChoosingPlayer/候选与校验；等待仍允许网络和选择继续处理。
- 核心去除 Unity Debug；正式输入校验不依赖编译条件 MyAssert。
- 验证纯核心可在无 Unity 引用的编译边界运行；按实际依赖选择 asmdef 或小型 .NET smoke harness，不建设独立服务器部署。

验收：相同输入的基础出牌、扣费、伤害、抽牌与 Hook 结果保持；等待选择可继续；可用无 UI 的入口驱动核心，状态推进不依赖帧率。

## 3. 固定最小协议与同步时序

- 定义握手版本/内容摘要、Join/Welcome、Ready/Start、CommandRequest、OrderedCommand、RequestOutcome、Choice、Disconnect 等必要消息语义，可合并消息类型但不遗漏语义。
- 消息明确序列化，不发送结构体原始内存或 GameAction 活对象；限制消息长度和未知枚举。
- 主机分配玩家槽位、初态与种子；连接绑定玩家身份。
- requestId 用于重试去重；CommandId 为主机权威序号。客户端导入该序号，禁止重新生成。
- 选择一种时序：主机在基础准入后定序并分发命令，各端在相同规则状态下串行执行，主机返回权威终态；不等待整条命令结束才通知客户端其开始，避免等待选择死锁。
- 对选择消息定义独立路由语义：执行器挂起时可处理匹配 ChoiceId 的选择，不能被普通待执行命令 FIFO 堵住；主机选择超时决策也作为统一输入传播。
- 权威定序分发与主机本地应用由单一调度点组织，主机消费一次；网络消息序号与普通命令完成进度不能混淆。

验收：用进程内传输连接两个互不共享可变状态的核心实例；乱序/重复缓冲行为明确；最终摘要一致；远端选择能解除挂起；非法请求不能冒用其他 Player。

## 4. 接 ENet 最小收发

- 从课程提取小型例子验证选定 C# 绑定、原生库和目标平台；不把完整课程服务器结构直接搬入项目。
- 实现 ENetTransport 的连接、消息、断开、轮询与资源清理；业务不持有 ENet Peer。
- 第一版关键业务消息统一可靠有序；先一个业务通道，不引入不必要通道与不可靠更新。
- 开发入口支持 host/connect 地址与端口、独立实例日志及存档路径，避免本机进程互相覆盖。

验收：一个主机进程 + 一个远端进程，完成握手、槽位分配和相同初态加载；双方都能提交出牌并看到一致结果。

## 5. 补齐最小房间流程与 UI 回应

- GameServer 管理人数、准备、开始状态，不另建 Realm。
- Client 接收房间状态、已分配本地玩家与权威结果，驱动 UI。
- 用 requestId/结果应用状态结束 Presenter 等待；其他玩家命令也触发状态刷新。
- 核心前进与 UI 动画分离；动画可排队，不得改变权威命令次序。

验收：两名玩家创建/加入、准备、开始、出牌、选牌；只有主机有开始权限，未就绪或版本不匹配不得开始。

## 6. 同步与失败场景收口

- 在相同已完成进度的稳定点比较状态摘要，包含必要的随机消费/规则状态，排除本地表现与录制时间戳。
- 确认同内容/同实现的随机结果；相同种子不作为唯一确定性证据。
- 测双端同时提交、重复请求、非法玩家/卡牌、等待选择、丢包/延迟、连接中断、发送积压。
- 请求与发送队列有界；结算忙时正常请求可排队，资源超限须明确拒绝/关闭，不无限增长。
- 第一版明确：主机退出结束房间；运行中重连/中途加入暂不支持，给出清晰提示；发现不同步则报告并中止，不默默继续。

验收：重复请求不重复扣费；双方应用顺序一致；掉线不永久卡死；主机退出有明确结束；慢客户端不堵住全局网络调度。

## 7. 按需求扩展

优先选择实际需要的一项，而非同时建设：
- 快照恢复：先定义稳定点快照、权威序号衔接、随机域恢复，再支持重连。
- Steam：新增平台房间/邀请服务与 SteamTransport；复用命令协议、GameClient/GameServer 和战斗核心。
- 独立 .NET 部署：更换启动入口和适配器；只有确有云端多局分配需求时才讨论 Realm/Agent。

## 首个里程碑

两个独立进程通过 ENet，完成创建/加入、开始战斗、双方出牌与选择，状态摘要一致；主机自身无特权写入路径。不要求 Steam、主机迁移、公网打洞或运行中恢复。

测试应围绕关键行为安排，不为纯目录移动或简单适配添加镜像测试；不能用仅能 echo 消息代替战斗同步验收。
