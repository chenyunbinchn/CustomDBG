2. 锁定的设计决策（来自本次问答）
------------------------------------------------------------------------

  决策 1【范围】：先修复 + 规范化；Execute 体保持 Debug.Log 桩，本轮不写
    真实战斗结算逻辑（扣 Hp / 加格挡 / 抽牌 / 能量 / 状态 / 消耗）。

  决策 2【状态访问方向】：Execute(BattleContext context) 传参。即便本轮
    Execute 体不读 context，也先把抽象签名、executor 传递、所有重写点一次性
    改到位，向前兼容（对应 GameAction.cs 的 Todo）。BattleContext 是 action
    运行时触达可变战斗状态的唯一通道。

  决策 3【ActionId / 初始状态约定】：每个 action 构造函数统一为
    (<payload>, ActionId id, EnumActionStatus status)；TranslateEffect 用
    actionManager.NextId() 取 Id、用 EnumActionStatus.WaitingForExecution 作
    初始状态。这让原本的死代码 GameActionManager.NextId() 正式被调用。

  决策 4【TryPlayCard 允许失败、不得崩溃】：出牌校验失败（不是玩家回合 /
    执行器忙 / 能量不足 / 找不到卡）是【预期的运行时失败】，不能用 MyAssert，
    一律 Debug.Log + return 让 UI 去提示。能量校验本轮只留 Todo 不实现。
    注意区分：TranslateEffect 内对「已知 EffectType 翻译成 null」「未知
    EffectType」用 MyAssert 保留——那是卡牌【数据错误】，属于该崩范畴。

  决策 5【多人游戏的 ActionManager 归属（开放）】：本轮按单一 GameActionManager
    实现，并在该类加 Todo 记录决策点。倾向：单一共享 ActionQueue 更好——动作
    需按单一全局顺序逐条结算，多队列会让全局执行顺序产生歧义、破坏回放确定性
    （见 CLAUDE.md 确定性随机/回放约束）。若将来确定要多队列，再回头改 NextId
    的归属。
