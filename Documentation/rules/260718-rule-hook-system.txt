  规则：Hook 事件系统（触发点 + 监听者 + 反应入队）

             存储与收集、触发时机、无差别广播+自过滤、反应翻译入队、
             入队位置、多 action×多监听者的确定性、死循环防护。

------------------------------------------------------------------------
1. 构成：监听者是数据，派发是无状态逻辑
------------------------------------------------------------------------
  1-1. HookListener 是纯数据：{挂在谁(Host)、监听哪个 Hook、过滤条件
       (Filter)、反应(Effect)}。反应的载体是 Effect 数据，不是函数 /
       委托——因为反应要能存进可序列化的战斗状态（联机/回放硬要求，
       见 battle-model 规则 §2）。禁止在 HookListener 上写方法或存委托。
  1-2. 派发是一段无状态的集中逻辑（静态类，只有函数无字段）。"执行反应"
       不分散在各监听者里，而是集中到唯一的翻译点。

------------------------------------------------------------------------
2. 存储与收集：监听者挂在实体身上，现场收集
------------------------------------------------------------------------
  2-1. 监听者存在实体身上（ICombatActor.HookListeners），属 transient 战斗
       状态，归实体持有（"state holds data"）。
  2-2. 派发入口全局唯一，但只是无状态静态类，不持有监听者列表。
       禁止建一个持有 HookListenerList 的全局 Manager——那会引入：施加/
       移除两处同步、忘注销的幽灵监听者、以及序列化时的对象引用重建。
  2-3. Fire 时现场遍历所有实体收集监听者（IterateHookListeners 的活）。
       实体死亡/移除，其监听者随之消失，零注销代码。

------------------------------------------------------------------------
3. 触发时机：模拟层的确定时刻
------------------------------------------------------------------------
  3-1. Fire 只允许发生在模拟层的确定时刻：命令执行内、action 执行内、
       回合边界。绝不在 UI / 表现层触发。
  3-2. 每个触发点调用一次 Fire。触发几次由"Fire 点放在哪"决定：Fire 放进
       action（如 DamageAction 内）= 每次该操作触发一次（每击）；Fire 放进
       命令展开（如出牌处）= 每张卡触发一次（每卡）。这是设计选择。

------------------------------------------------------------------------
4. 派发机制：无差别广播 + 接收方自过滤
------------------------------------------------------------------------
  4-1. Fire 不维护"谁在听某事件"的名单。它遍历所有在场监听者，每个监听者
       用自己的 Hook 字段匹配事件类型、再用 Filter 字段判断与持有者的关系，
       自行决定是否响应。tag（关心哪个 Hook）长在监听者身上，不在发送方。
  4-2. 遍历顺序固定且唯一：玩家按 index → 敌人按 index → 同一宿主内按
       HookListeners 列表序。这是确定性的唯一来源。禁止用 Dictionary 等
       无序容器存监听者、禁止依赖不稳定的遍历序。

------------------------------------------------------------------------
5. 事件上下文与自过滤
------------------------------------------------------------------------
  5-1. Fire 携带事件上下文 HookEvent（值类型）：至少含
       {EnumHookType Hook、ActionEntityId Source(引发者)、
        ActionEntityId Target(承受者)、int Value(数值)}，供监听者自过滤。
  5-2. 过滤条件用枚举字段 EnumHookFilter（Always / SelfIsSource /
       SelfIsTarget / …），不用委托。过滤的判断代码集中写在派发逻辑里
       （一个对照 Filter 与 HookEvent 的 switch）；监听者只携带条件，
       不携带判断方法。新过滤种类 = 加一个枚举值 + 一个 case。

------------------------------------------------------------------------
6. 反应机制：翻译成普通 GameAction 入队，不立即执行
------------------------------------------------------------------------
  6-1. 命中的监听者不当场执行反应，其 Effect 经 EffectApi.Translate 翻译成
       普通的具体 GameAction（GainBlockAction / DamageAction …）入队，
       不包装成特殊的 "HookAction" 类型——执行器/回放/网络看到的是单一
       action 流，不区分来源。
  6-2. 反应 action 由既有的串行结算排空（battle-model 规则 §3）：反应可再
       触发反应、层层入队，全部在同一条命令的稳定点（队列干涸）内跑完。
       这不是 Dota2 式的同步递归回调；用"翻译入队"替代它，避免重入。

------------------------------------------------------------------------
7. 入队位置：默认尾插，头插用于插队
------------------------------------------------------------------------
  7-1. 反应 action 默认尾插（GameActionManager.Add）。顺序确定，多数反应
       与队列剩余 action 不相干，尾插看不出差别。
  7-2. 仅当"反应必须抢在某个已排队的、与它相互作用的 action 之前生效"时，
       才需要头插——用监听者上的字段 EnumEnqueueMode{Tail, Head} 表达，
       翻译时按它调 Add / AddFirst（AddFirst 待加）。
  7-3. 入队模式是每个监听者自己的属性：同一 Hook 下不同监听者可要不同
       模式（一个要插队防下一击、一个不在乎）。不做全局或按-Hook 的一刀切。
  7-4. 头插给出深度优先结算（反应及其后果先于兄弟 action 全部展开）。
       推迟实现：第一个顺序敏感的效果出现再加 EnumEnqueueMode + AddFirst。

------------------------------------------------------------------------
8. 多 action × 多监听者的确定性
------------------------------------------------------------------------
  8-1. 最终执行顺序由三层唯一确定：（action 执行序）×（每个 action 的
       Fire 点）×（一次 Fire 内的监听者遍历序）。无歧义、无竞态、无需特殊
       处理。
  8-2. Fire 只入队、不执行，故遍历监听者列表期间列表本身不被改动（反应要
       等它作为 action 被弹出执行时才可能加/减监听者）。每次 Fire 看到的
       是那一刻稳定的监听者快照——多 action 连环触发不会出现"边遍历边改
       集合"的重入 bug。

------------------------------------------------------------------------
9. 反应死循环防护
------------------------------------------------------------------------
  9-1. 自过滤事件模型下，监听者可能互相触发成环（如双方都有"受击反伤"，
       A 打 B → B 反伤 A → 触发 A 反伤 → …），队列永不干涸、稳定点到不了。
  9-2. 应对优先级：
       a) 首选——用 Fire 点 / Filter 设计从触发条件上断环（如反伤只对
          "攻击类"伤害触发、反伤本身不属该类）；
       b) 重入守卫——同一条命令的结算链内，同一监听者最多触发 N 次；
       c) 兜底——单条命令展开的 action 总数封顶，超限 MyAssert 断言。
