1. 背景与引言
------------------------------------------------------------------------

本项目的 Seed 结构体使用 uint 作为内部值类型，而 System.Random
的构造函数接受 int 参数。两者之间的转换引发了一个设计问题：
Seed 应该用 uint 还是 int？

这个问题背后涉及更深层的选择哲学：
  - .NET 为什么大量使用 int 而非 uint？
  - uint 和 int 各自在表达什么语义？
  - 在什么场景下该选哪个？

------------------------------------------------------------------------

2. uint 和 int 的本质
------------------------------------------------------------------------

2.1 二进制层面：完全相同

int 和 uint 在内存中都是 32 位（4 字节）二进制数据。
区别只在于"如何解读这 32 位"：

  二进制：               11111111 11111111 11111101 00001110
  解读为 int（有符号）：  -754
  解读为 uint（无符号）： 4294966542

同样的二进制，两种解读方式。

2.2 范围差异

  int:   -2,147,483,648  到  2,147,483,647   （约 -21亿 到 +21亿）
  uint:               0  到  4,294,967,295   （约 0 到 42亿）

  两者能表示的"数量"相同（都是 2^32 = 4,294,967,296 个值），
  但 int 把一半给了负数，uint 把全部给了正数。

------------------------------------------------------------------------

3. .NET 为什么偏爱 int
------------------------------------------------------------------------

在 .NET 标准库中，几乎所有 API 都使用 int：

  System.Random.Next(int maxExclusive)     — int
  List<T>.Count                            — int
  Array.Length                             — int
  string.Length                            — int
  for (int i = 0; i < n; i++)             — int

即使这些值在语义上"不可能为负"（数组长度不可能是 -3），
.NET 仍然选择 int。原因如下：

3.1 CLS 兼容性（Common Language Specification）

.NET 被设计为多语言平台（C#, VB.NET, F# 等）。
CLS（公共语言规范）规定了所有 .NET 语言必须支持的类型集合。

uint 不是 CLS 兼容类型。也就是说：
  - 某些 .NET 语言可能不支持 uint
  - 用 uint 作为公共 API 参数，这些语言的用户无法调用

因此 .NET 标准库的所有公共 API 都避免使用 uint。
这是历史和生态兼容性的决策。

3.2 混合运算的隐患

int 和 uint 混合运算时，C# 的隐式转换规则会产生意外行为：

  int a = -1;
  uint b = 1;

  // a + b 的类型是什么？
  // C# 会把 int 隐式转换为 uint：
  // (uint)(-1) = 4294967295
  // 4294967295 + 1 = 4294967296 → 溢出为 0

  // 更危险的：
  if (a < b)  // -1 < 1？
  {
      // 你以为会进来，但实际上：
      // (uint)(-1) = 4294967295
      // 4294967295 < 1 → false！
      // 不会进来！
  }

如果整个代码库都用 int，就不会遇到这类混合运算的陷阱。
这是 .NET 选择 int 的最实际的原因。

3.3 减法结果自然为负

  int remaining = list.Count - index;

  如果 Count 和 index 都是 uint，当 index > Count 时：
    uint result = 5u - 10u;  // 不是 -5，而是 4294967291（下溢）

  用 int 时：
    int result = 5 - 10;  // -5，符合直觉

  很多算术操作的中间结果可能为负，int 能自然处理，uint 会下溢。

3.4 API 一致性

  如果 Array.Length 是 uint 而 for 循环的 i 是 int，
  你需要到处写强制转换：

    for (int i = 0; i < (int)array.Length; i++)  // 烦

  统一用 int，所有地方自然兼容，无需转换。

------------------------------------------------------------------------

4. uint 的适用场景
------------------------------------------------------------------------

虽然 .NET 偏爱 int，但 uint 在某些场景下有明确优势：

4.1 位操作和标志位

  uint flags = 0xFFFFFFFF;  // 32 个标志位全部为 1
  flags & 0x80000000;       // 检查最高位

  用 int 做位操作时，最高位是符号位，语义混乱。
  uint 的 32 位都是"数据位"，语义清晰。

4.2 哈希值

  哈希函数的输出是"无意义的二进制模式"，不表示数量大小。
  用 uint 更合适——不存在"负哈希"的概念。

4.3 网络协议和二进制格式

  网络包头中的字段（如消息长度、序列号）通常定义为无符号。
  用 uint 和协议规范对齐。

4.4 需要完整 32 位正数范围

  如果你需要表示 0 到 42 亿的值（int 最多 21 亿），
  uint 提供两倍的正数范围。

------------------------------------------------------------------------

5. Seed 该用 uint 还是 int
------------------------------------------------------------------------

5.1 选 uint 的理由

  - "种子"在语义上是一个标识符/起点，不是"数量"
  - 没有"负种子"的概念
  - 和哈希值类似，是无意义的二进制模式
  - STS2 的 Rng 类使用 uint seed

5.2 选 int 的理由

  - System.Random 构造函数接受 int，直接传入无需转换
  - DeterministicHash 返回 int，直接存入无需转换
  - 整个 .NET 生态是 int 为主，用 uint 需要到处转换
  - 种子的值本身没有大小意义，用 int 还是 uint 不影响功能

5.3 转换链分析

当前使用 uint 时的数据流：

  DeterministicHash("42shuffle")
    → 返回 int（可能为负）
    → (uint)hash 转为 uint 存入 Seed
    → new System.Random((int)seed.Value) 又转回 int

  一共经过了两次强制类型转换。二进制不变，功能正确，
  但代码中出现了 (uint) 和 (int) 的来回转换，不够干净。

如果使用 int 时的数据流：

  DeterministicHash("42shuffle")
    → 返回 int
    → 直接存入 Seed
    → new System.Random(seed.Value) 直接传入

  零次强制类型转换。

5.4 STS2 怎么做的

来源：D:\Decompiled Projects\Slay the Spire 2\src\Core\Random\Rng.cs

  public Rng(uint seed = 0u, int counter = 0)
  {
      Seed = seed;
      _random = new System.Random((int)seed);   // uint → int 转换
      FastForwardCounter(counter);
  }

STS2 选择了 uint，然后在传给 System.Random 时做 (int) 转换。
这说明 STS2 认为"种子语义上是无符号的"这一点更重要，
接受了一次类型转换的代价。

------------------------------------------------------------------------

6. 方案对比
------------------------------------------------------------------------

  方案          | Seed.Value 类型 | 转换次数 | 语义清晰度 | API兼容性
  --------------|----------------|----------|-----------|----------
  A. 用 uint    | uint           | 2次      | 好（无负种子）| 差（需转换）
  B. 用 int     | int            | 0次      | 中（可能为负）| 好（直接传）

  两种方案功能完全等价。区别只在代码风格和阅读体验。

------------------------------------------------------------------------

7. 结论
------------------------------------------------------------------------

两种选择都是正确的。核心权衡是：

  uint：语义更纯粹（种子不应该有正负之分），
        但和 .NET API 有摩擦（需要类型转换）。
  int： 和 .NET 生态无缝衔接，
        但接受了"种子值可能显示为负数"的不优雅。

建议：保持当前的 uint 设计。理由：
  - 与 STS2 一致
  - 类型转换只发生在 SeedHelper 和 RandomManager 的内部，
    不会暴露给外部调用者
  - 强制转换虽然存在，但不会导致 bug（二进制不变）
  - Seed 作为值类型，"无符号"的语义更准确

如果你觉得 (int)(uint) 的转换让代码不够干净，
换成 int 也完全没问题——功能无差异。
