1. 背景与引言
------------------------------------------------------------------------

3. 方案概览：分类改造方向
------------------------------------------------------------------------

  3.1 玩家身份（一类 1-1 ~ 1-3）
    赋编号：StateManager.Init 的循环里
      BattlePlayerStates[i].Id = new ActionEntityId(Player, (uint)i)，
    一行改动。Resolve 需要拿到全部玩家，两个方案：
    方案 A：EntityApi.Resolve 签名加 BattlePlayerState[] 参数。
      优点：改动最小。缺点：每个调用方（每个 action.Execute）都要多
      传一个参数，参数链继续变长。
    方案 B：BattlePlayerState[] 挂进 BattleState（它本来注释就是
      shared by all players），Resolve 只收 BattleState。
      优点：战斗范围的状态自包含，全线签名收敛；BattlePlayerStates
      本就是 transient，归属一致。缺点：StateManager 与 BattleState
      各持一份引用，Reset 时要保证同步。
    【已决策 2026-07-17】采用方案 B；玩家编号统一用 ActionEntityId
    （EnumPlayerIndex 已从代码库删除）。

  3.2 action 执行链（二类 2-1 ~ 2-3）
    方案 A：Execute(BattleState)（BattleState 已含玩家数组），作用于
      玩家的 action 一律自带 ActionEntityId Target，经 Resolve 找人。
      优点：改动小、与 Damage/GainBlock/ApplyStatus 现状一致。
      缺点：将来 action 需要随机数/入队新 action 时还要再改签名。
    方案 B：Execute(BattleContext)，BattleContext 聚合
      {BattleState, BattlePlayerState[], RandomManager,
       GameActionManager}。
      优点：签名只改这一次，hook 反应入队、抽牌重洗取随机都有出口。
      缺点：上下文对象要新建并在 EnterBattle 时组装。
    倾向 B（签名改动是全子类连锁，宜一次到位）。
    无论 A/B：CostEnergy/GainEnergy/Draw/DiscardHandCard 四个 action
    补 ActionEntityId Target 字段，EffectApi.Translate 对它们也走
    ResolveTargetId（EffectApi.cs:20-31 现在不传 target）。

  3.3 玩家选择输入（二类 2-4）
    HandCardChooseAction 加 ActionEntityId ChoosingPlayer；完成条件从
    "本地字段被写入"改为"收到该玩家的 ChooseCardCommand"——本地 UI 的
    点击与远端网络消息汇合到同一条命令，与出牌命令同一套提交点。

  3.4 输入命令化（三类 3-1 ~ 3-3）
    结论沿用 2026-07-17 会话讨论：
    - PlayCardCommand {ActionEntityId Player; CardInstanceId Card;
      ActionEntityId Target} 纯值类型，即网络消息本身；
    - 本地与远端同一提交点，主机无特权路径（已写入 CLAUDE.md）；
    - CanPlayCard(state, cmd) 一个函数两用：UI 预检 + 执行前权威校验；
    - executor 忙碌时命令排队等待，绝不丢弃；规则性拒绝（回合/能量）
      才允许失败；
    - UnityBoostrap 的键盘测试输入改为构造命令投进提交点（测试代码
      成为最早的命令生产者）；
    - 打出的牌移入弃牌堆收进命令执行内（action 化，缺一个"打出后归弃"
      action 类型，与 DiscardHandCardAction 的"弃牌"语义区分）。
    命令结构（单 struct+枚举 vs 每命令一类型）的取舍见会话结论：倾向
    单 struct + EnumCommandType（与 Effect 先例一致，序列化单一路径）。

  3.5 队列与 ActionId（五类 5-2）
    采用单共享 ActionQueue：action 全局顺序=战斗事实顺序，回放与同步
    都以它为准；每玩家队列需额外定义跨队列合并顺序，是自找复杂度。
    定下后 GameActionManager.NextId 维持现状，删 Todo。
    【已决策 2026-07-17】采用单共享队列，模拟全局战斗顺序。

  3.6 Id 唯一性（五类 5-1）
    方案 A：保持玩家范围 CardInstanceId，一切跨玩家引用强制带
      ActionEntityId 玩家限定（网络消息/回放行 = Player+Card 二元组）。
      优点：零迁移。缺点：每处跨玩家引用都要记得带限定，漏带即歧义。
    方案 B：恢复全局 Id 生成（单一计数器挂 GameState 或专门管理类），
      CardInstanceId 全局唯一。
      优点：引用自包含，回放日志可读性好。缺点：计数器成为需要存档、
      需要随对局初始化同步的状态。
    不急于定：第一个跨玩家卡牌引用（效果或消息）出现时再选。
    【已决策 2026-07-17】倾向方案 A，暂不实施；已在
    CardDeck.GenerateId 与 CardPileManager.AddCard 加 Todo 注释。

  3.7 随机与种子（五类 5-3、六类 6-1）
    种子：对局初始化消息携带主机生成的 MainSeed，SeedManager.Init 收
    它；41u 写死仅限本地测试。
    随机域：
    方案 A：维持全局共享域 + "全端同序执行"纪律。listen server 主机
      单点模拟下自动满足，零改动。
    方案 B：每玩家一套域（SeedManager 按玩家下标派生 shuffle_p0、
      shuffle_p1 …）。玩家间随机隔离，断线重连/局部重放容易；代价是
      域数量×人数、SeedManager 派生逻辑改造。
    listen server 下 A 够用；若将来做客户端预测/局部重放再升 B。
    【已决策 2026-07-17】采用方案 A（全局共享域 + 全端同序执行）。

  3.8 回合结构（四类 4-1）
    等玩法形式定，两个候选先记录：
    - versus 轮流制：BattleState.CurrentPlayerIndex（int），命令校验
      即"cmd.Player == CurrentPlayerIndex"。
    - co-op 同时行动：EnumTurnPhase（玩家阶段/敌人阶段）+ 每玩家就绪
      标记，玩家阶段内全员可出牌，全员就绪进敌人阶段。
    命令化先落地时，CanPlayCard 里给回合校验留一个函数位即可。
    【已决策 2026-07-17】采用同时行动制，并确立命令串行结算规则：
    一条出牌命令的全部后果（展开的所有 GameAction，含执行中新产生
    的）结算完毕、action 队列彻底为空（稳定点）之后，才执行下一条
    命令。要点：
    a) "全部执行完毕"的判定是 action 队列干涸，不是入队那一刻的
       条数——action 执行中还会产生新 action（如将来 DamageAction
       触发受伤 hook、反应再入队），条数是动态增长的。
    b) 其他玩家的出牌命令在此期间【排队，不拒绝】：串行点在命令
       队列的出口，不在入口；已提交的命令绝不丢弃。
    c) 权威校验在命令轮到执行时做：前一条命令的结算可能改变本命令
       的合法性（想打的牌被弃、能量被扣），非法则丢弃——各端状态
       一致，丢弃结果也一致。
    d) 例外：等待玩家选择的 action（HandCardChooseAction）挂起队列
       时，该玩家的"选择命令"是喂给挂起 action 的输入、直接消费，
       不受稳定点约束；其余玩家的出牌命令继续排队。联机下选择需要
       超时（超时自动选/跳过），防一名玩家掉线卡死全场。
    e) 同时行动 = 任意顺序的串行：主机按命令到达先后定序，不存在
       "同一瞬间"，一切效果严格先后结算。

4. 结论
------------------------------------------------------------------------

  单人假设集中在三处：玩家身份（全员 Player#0、Resolve 不看编号）、
  action 执行链（单玩家上下文贯穿基类签名）、输入入口（未命令化、
  写死玩家 0）。状态容器层（StateManager / GamePlayerState /
  BattlePileApi / HookApi）已是多人形态，无需动。

  建议顺序：
  ① 赋玩家 Id + Resolve 多玩家化（1-1、1-2，改动最小、其余一切的
    前提）；
  ② 出牌命令化（3-1 ~ 3-3，联机输入通道的根）；
  ③ action 执行链签名一次性改造（2-1 ~ 2-4）；
  ④ 回合结构（4-1，等玩法形式）；
  ⑤ Id/随机域（5-1、6-1）按"第一个用例出现时再定"处理。
