  GameAction 全量缺口审计报告
  日期：2026-09-03

审计基线：当前工作区已包含 DrawCardAction 的确定性抽牌修复与
BattleActionContext。审计对象为 Assets/Scripts 下全部 GameAction 子类，并向外检查
EffectApi、BattleCommandApi、ActionExecutor、BattlePileApi、HookSystem、状态容器和现有
战斗规则。

严重级别：
  P0：启用后会卡死、崩溃或造成联机/回放状态分叉。
  P1：会直接产生错误战斗结果，或阻塞现有战斗闭环。
  P2：当前基础行为可用，但规则、扩展性或防御性不完整。
  P3：工程质量、诊断和性能问题。

------------------------------------------------------------------------
1. 结论
------------------------------------------------------------------------

当前共有 10 个 GameAction 子类：

  纯占位、没有业务状态修改：
    - DiscardHandCardAction
    - ExhaustCardAction

  控制流占位、当前不可安全使用：
    - HandCardChooseAction

  已修改状态，但核心规则错误或缺失：
    - DamageAction
    - ApplyStatusAction
    - PlayedCardToDiscardAction

  最小路径已工作，但仍有规则缺口：
    - CostEnergyAction
    - GainEnergyAction
    - DrawCardAction
    - GainBlockAction

此外存在 8 组跨 Action 的系统问题：目标验证与多目标展开、隐式玩家归属、Action
载荷缺少来源、执行异常会锁死、选择状态机没有入口、Hook 触发时机过早、战斗结束与
跨战斗重置缺失、自动化测试为空。这些问题不能只在某一个 Execute() 内打补丁解决。

当前 cards.json 的 5 张测试卡中：

  - “剑柄打击”的抽牌已修复。
  - “攻击”“剑柄打击”“连斩”的伤害会绕过目标格挡，也不会触发死亡/胜负结算。
  - “残影”在单次、Value=2 的样例下表面可用，但实际使用的是 StatusRegistry 写死的
    2，ApplyStatusAction.Value 没有生效；重复施加只是重复添加监听器。
  - 当前没有配置 Exhaust 或 Discard 效果的卡，所以两个占位实现暂时是潜伏故障。

2.1 DamageAction：部分实现，P1

证据：Assets/Scripts/action/gameEffectActions/DamageAction.cs:23-31。

当前行为：Resolve 目标后直接执行 target.Hp -= Value。

问题：
  D-01. 完全绕过 Block。现有战斗需求明确规定“先扣格挡，溢出伤害再扣 Hp”。
  D-02. 没有把 Hp 限制到合法范围，也没有死亡标记、敌人移除、玩家失败或全部敌人
        死亡后的胜利判断。
  D-03. Action 只有 Value 和 Target，没有 Source、来源卡牌或伤害属性，无法正确计算
        Strength/Weak/Vulnerable、攻击类限定、反伤和来源过滤 Hook。
  D-04. 目标敌人不存在时静默跳过并被执行器标记 Finished。非法目标、目标在前序
        Action 中死亡、允许的 fizzled hit 三种语义没有区分。
  D-05. Value 没有非负校验；负伤害会直接治疗目标。
  D-06. 没有每击的 Before/AfterDamage Hook，因此“连斩”的两次伤害不能形成两个明确
        伤害事件。

影响：当前任何带格挡的敌人都会受到错误 Hp 伤害；战斗无法由伤害自然进入胜负状态。

2.2 GainBlockAction：最小实现，P2

证据：Assets/Scripts/action/gameEffectActions/GainBlockAction.cs:23-31。

当前行为：Resolve 目标后执行 target.Block += Value。

问题：
  B-01. 没有非负校验；负 Value 会绕过专门的失去格挡语义直接减格挡，并可能得到负数。
  B-02. 没有 Source、来源卡牌和 Block 属性，无法接入未来的 Dexterity/Frail 等修改器。
  B-03. 目标不存在时静默完成，没有区分非法目标与合法失效。
  B-04. 没有 GainBlock 前后 Hook 或结果值，表现层和反应系统不知道实际获得多少格挡。
  B-05. 多目标类型依赖 EffectApi，但目前 AllAllies/AllEnemy 等会被错误退回 picked。

影响：“防御”当前能增加 5 格挡，但无法保证更复杂状态、负数配置和多目标卡的正确性。

2.3 CostEnergyAction：最小实现，P2

证据：Assets/Scripts/action/gameEffectActions/CostEnergyAction.cs:21-27；
      Assets/Scripts/systems/BattleCommandApi.cs:79,106。

当前行为：出牌命令先校验费用，再入队扣除当前命令玩家的能量。

问题：

------------------------------------------------------------------------
3. 跨 Action 的系统问题
------------------------------------------------------------------------

3.1 X-01：目标验证缺失，P1

BattleCommandApi.CanPlayCard 只校验回合、卡、手牌和能量，没有验证目标是否存在、存活、
类型是否匹配卡牌每个 Effect.TargetType。BattlePresenter 当前默认选择 EnemyList[0]。

结果：SelectedEnemy 可以收到 default/玩家/死亡敌人 Id；命令仍支付费用并打出卡，
DamageAction 可能静默 no-op。

3.2 X-02：多目标和随机目标被错误降级，P1

EffectApi.ResolveTargetId 只实现 Self/User/SelectedEnemy；AllEnemy、RandomEnemy、
SelectedAlly、AllAllies、None 全部默认返回 picked。RandomEnemy 不消耗确定性 RNG，
AllEnemy/AllAllies 也不会展开多个 Action。

结果：配置可以成功加载，但效果含义错误。应在数据加载期拒绝尚未支持的组合，不能静默
退回 picked。

3.3 X-03：Context 当前玩家被误当作 Action 语义目标，P1

BattleActionContext.PlayerState 表示“产生整批 Action 的命令玩家”，适合 CostEnergy 和
PlayedCardToDiscard 的现有调用，但不是所有反应 Action 的目标。HookSystem 会以
HookListener.Owner 作为 Effect source；如果 Owner 不是命令玩家，GainEnergy、Draw 和
未来 Discard 仍会操作 context.PlayerState，写错实体。

原则：Context 提供执行服务和世界状态；“谁受到这个 Action”必须是 Action 自己的显式
Id 载荷，不能从批次 Context 猜测。

3.4 X-04：Action 载荷缺少来源和来源卡，P1/P2

Damage/GainBlock/ApplyStatus 有 Target，但没有 Source 与 SourceCard；Draw/GainEnergy/
CostEnergy/PlayedCardToDiscard 又依赖隐式玩家。修改器、Hook 过滤、日志、回放诊断、
Exhaust Self 都缺少因果信息。

建议统一最小来源结构：SourceActorId + 可选 SourceCardId；每个需要目标的 Action 再携带
显式 TargetActorId/TargetCardIds。

3.5 X-05：ActionExecutor 异常后会永久锁死，P0

ActionExecutor.Run 没有 try/finally。Action 已从队列移除后，只要 Execute 抛异常，
IsRunning 不会恢复 false，ActionStatus 留在 Executing，BattleCommandApi.Pump 永久返回。
执行器也没有 CurrentAction、失败状态或恢复/终止策略。

另外，ActionExecutor 在 coroutine 返回后无条件写 Finished，会覆盖 Action 自己可能设置的
Canceled 等终态；ActionStatus 目前不是受约束的状态机。

3.6 X-06：Effect 数据验证依赖开发断言，Release 可入队 null，P0

EffectApi 对 None、CostEnergy 和未知枚举只调用 MyAssert，然后继续 Add(action)。
MyAssert 带 Conditional(UNITY_EDITOR/DEVELOPMENT_BUILD)，Release 调用会被移除，因此
action 仍为 null 并被加入队列；执行器随后访问 action.ActionStatus 抛 NullReference，
再触发 X-05 锁死。CardDefinitionManager 只验证 effects 数组非空，没有验证合法的
EffectType/TargetType/StatusType/Value 组合。

3.7 X-07：Hook 的 AfterCardPlayed 在 Action 执行前就被收集，P1/P2

BattleCommandApi 在“创建 Action 队列”阶段调用 HookSystem.Fire。此时费用尚未扣、效果尚未
执行、卡也仍在手牌。虽然反应 Action 排在卡牌自身 Action 后面执行，但“哪些监听器命中”
已经按旧状态决定。

这会导致：本次效果移除/禁用监听器仍可能触发；本次效果新建监听器一定看不到事件；
事件上下文 Value 固定为 0；Hook 不是在实际完成出牌的模拟时刻产生。应将 Fire 放入明确的
CardPlayedAction/出牌收尾 Action 执行点，或固化“展开时快照”规则并接受其语义。

3.8 X-08：没有胜负检查、展开上限、跨战斗清理和自动测试，P0/P1

  - 执行器没有每个 Action 后的 BattleRuleSystem/CheckWinCondition。
  - Hook 规则要求对单命令展开 Action 数设上限防止反应死循环，当前没有实现。
  - EnterBattle 不清空 ActionQueue、Pending commands、CurrentAction/IsRunning，也没有定义
    异常中断后如何进入下一场；GameState.IsInBattle 没有有效读写。
  - 项目中没有 Action 自动化测试程序集或测试文件。

4. 推荐修复顺序
------------------------------------------------------------------------

第一阶段，先防止错误继续扩散：
  1. 增加 Effect/Target 数据加载期验证，禁止 null Action 入队。
  2. ActionExecutor 增加 CurrentAction、try/finally、明确失败终态和单命令 Action 上限。
  3. 增加 PlayCard 目标合法性验证。

第二阶段，修正卡牌生命周期与缺失牌堆 Action：
  1. 引入 PlayPile 和 Hand -> Play 的独立 Action。
  2. 牌堆移动统一使用 CardInstanceId，不使用手牌下标。
  3. 实现 Exhaust Self、指定卡消耗、弃牌和出牌最终目的地。
  4. 用 ChoiceCommand 重建 HandCardChooseAction，增加选择玩家、ChoiceId、候选 Id、
     取消和由主机决定的超时结果。

第三阶段，修正数值与状态：
  1. Damage 先扣 Block，再扣 Hp，返回 DamageResult；每击后做死亡与胜负检查。
  2. 建立 StatusStack 存储和 Amount 规则，Afterimage 使用实际 Value。
  3. 接入 Weak/Vulnerable/Power 的确定性 modifier chain。
  4. 定义 GainBlock/GainEnergy/Draw 的上限、负值和实际结果规则。

第四阶段，补齐目标与反应：
  1. Action 显式携带 Source、Target 和可选 SourceCard。
