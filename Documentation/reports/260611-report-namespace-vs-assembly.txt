  报告：C# 的 namespace 与 assembly 的关系
  生成日期：2026-06-11

1. 背景与引言
------------------------------------------------------------------------

讨论"洗牌放哪一层、谁依赖谁、循环依赖怎么解"时，反复撞到一个底层
问题：在 C#（尤其在 Unity 里）所谓的"依赖""循环"到底是什么层面的？
是命名空间，还是程序集？谁会让你真正编译失败？本报告厘清 namespace
与 assembly 的区别与关系，这是前述所有分层结论成立的前提。

------------------------------------------------------------------------

2. 代码分析（项目现状）
------------------------------------------------------------------------

2.1 本项目没有 asmdef，全在一个程序集

  Glob 'Assets/**/*.asmdef' 结果：无。
  意味着所有脚本都被编进预定义的 Assembly-CSharp（及 -Editor /
  -firstpass）。tools / random / cards / gameStates / systems 等命名空间
  实际都挤在同一个 dll 里。

2.2 命名空间现状与一条关键依赖

  来源：Assets/Scripts/random/RandomManager.cs 第 1 行 `using tools;`
  逻辑上 random 依赖 tools。但因为它们在同一个程序集里，这条"依赖"
  并不被编译器当成需要无环的边——见下。

------------------------------------------------------------------------

3. namespace 与 assembly 的本质
------------------------------------------------------------------------

3.1 namespace —— 纯命名

  - 只是给类型名做逻辑分组、避免重名。namespace cards.api { class X }
    的效果就是类型全名变成 cards.api.X。
  - 不带依赖语义、不带物理边界、不带访问控制（除名字本身）。
  - 一个 namespace 可横跨任意多个文件、甚至任意多个 assembly。
  - C# 编译器【没有】"namespace 循环依赖"这个概念：同一程序集内，
    namespace X 的类型与 namespace Y 的类型可以自由互相引用。
  - using 只是把名字导进来少打字，不产生编译器强制无环的"依赖边"。

3.2 assembly —— 真正的编译与依赖单元

  - 编译/部署的单位：一个 .dll（或 .exe）。C# 编译器吃"一批源文件 +
    一批被引用 assembly"，吐出一个 assembly。
  - 真正的边界都在这层：
      * assembly 引用必须【无环】：A→B→A 是编译错误。构建系统要求
        程序集之间是 DAG。这才是"环会让你编不过"的那个环。
      * internal 访问修饰符 = "仅本 assembly 可见"。assembly 是 internal
        的边界。
      * 每个 assembly 单独编译 → 增量编译：改一个，只它和依赖它的重编。

3.3 推论（直接影响分层决策）

  在单 Assembly-CSharp 下：
  - 我们说的"tools↔random 循环依赖"是【逻辑/自律】层面的环，编译器
    不拦。你今天就能把洗牌放 tools 里直接 using random 并编过。
  - 因此"拆 tools.assert / tools.shuffle 来解环"只在 namespace 粒度
    把逻辑理顺，是【文档与自律】，不解锁任何编译能力，也不强制任何
    约束。
  - 要让"tools 不许依赖 random"变成编译错误，必须把它们拆成独立
    assembly（asmdef），并在引用列表里不写 random——那时环才有牙齿。

------------------------------------------------------------------------

4. 何时靠哪个
------------------------------------------------------------------------

  目标                              手段
  --------------------------------  ----------------------------------
  组织名字、避免重名、表达意图      namespace（够用，零成本）
  按约定分层、画依赖图              namespace + 团队自律
  让分层规则变成编译错误（强制）    asmdef（独立 assembly，见专门报告）
  让 internal 真正生效              拆 assembly

------------------------------------------------------------------------

5. 结论
------------------------------------------------------------------------

namespace 管命名，assembly 管依赖与编译；真正会编译失败的环是
assembly 级（asmdef/项目引用），永远不是 namespace 级。本项目当前
单程序集，所有分层都是约定与自律，没有强制力——这对小项目是合理的。
若将来要强制分层，需上 asmdef（见《260611-report-unity-assembly-and-
asmdef-organization》），届时今天规划好的 namespace 分层会顺势成为
asmdef 的边界。
