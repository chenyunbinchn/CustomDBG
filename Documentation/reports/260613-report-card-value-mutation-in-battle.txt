========================================================================
  报告：战斗中卡牌自身数值变化的存放方案
  生成日期：2026-06-13
========================================================================

1. 背景与引言
------------------------------------------------------------------------

战斗中存在"修改某张卡自身数值"的效果，例如：

  某张卡使 A 卡在此次战斗中伤害永远 +2。

CardDefinition 是只读模板，装不下这种运行期变化。问题是：这个
"+2"存在哪里？怎么读？战斗结束怎么还原？

先厘清一个关键区分（本报告的边界）：

  【改卡】  ——"A 卡伤害 +2"：改的是这张卡的属性，有明确生命周期
            （本场战斗/本局/永久），卡面数字直接变。是【状态】。
  【改结算】——力量 +2、易伤 x1.5：改的是每一次伤害事件，数值来源
            是单位身上的状态，每次结算时重算。是【计算】。

改结算已由《260609-report-modifier-chain》覆盖（修改器链/Hook）。
本报告只讨论【改卡】。两者是两条独立管道，不混用。

------------------------------------------------------------------------

2. 代码分析
------------------------------------------------------------------------

2.1 本项目现状

  来源：Assets/Scripts/cards/instance/CardInstance.cs
    public class CardInstance {
        public CardDefinition Definition;   // 只持引用，数值全在模板里
        public CardInstanceId Id;
        public EnumEnchantmentType Enchantment;
    }
  来源：Assets/Scripts/cards/effects/CardEffect.cs
    public struct CardEffect { ... public int Value; }   // 编辑期固定

  数值唯一来源是 Definition.CardEffect[]，实例层没有可变数值的容身处。
  另注意：CardInstance 由 CardInstanceManager 持有，属【持久层】
  （跨战斗存活），任何战斗期写入都有"战斗结束变脏"的问题。

2.2 STS2 的做法（实例可变数值 + Hook 两层并用）

  来源：D:\Decompiled Projects\Slay the Spire 2\src\Core\Localization\
        DynamicVars\DynamicVar.cs
    public class DynamicVar {
        private decimal _baseValue;                  // 可写
        public decimal BaseValue { get; set; }
        public void UpgradeValueBy(decimal addend) { BaseValue += addend; }
    }
  每个 CardModel（卡牌实例）挂 DynamicVars（Damage/Block/Repeat 等），
  BaseValue 运行期可写。

  来源：src\Core\Models\Cards\SovereignBlade.cs:203
    public void AddDamage(decimal amount) {
        base.DynamicVars.Damage.BaseValue += amount;   // 改卡=写实例状态
        CurrentDamage = base.DynamicVars.Damage.BaseValue;
    }

  而力量/易伤等仍走 Power 的 ModifyDamageAdditive/Multiplicative Hook
  （见《260609-report-modifier-chain》2.1 节）。即 STS2 的答案：
  【改卡写实例自身的可变数值；改结算走修改器链】，
  最终伤害 = 卡的当前 BaseValue → 再过修改器链。

3. 全部可行方案
------------------------------------------------------------------------

────────────────────────────────────────────────────────────────────
方案 1：实例可变数值（STS2 做法）
────────────────────────────────────────────────────────────────────
原理：CardInstance（或其战斗副本）创建时从 Definition 拷贝数值，
      "+2"直接写实例字段。
优点：
  - 读路径单一："这张卡伤害是多少"一次读取回答，不是每次现场推导。
  - UI 显示天然正确；调试看一眼字段即知；STS2 验证过。
缺点：
  - 本项目 CardInstance 是持久层，"本场 +2"需要还原机制（见下方
    子方案 1a/1b）。
作用域子方案：
  1a 战斗副本（推荐）：战斗开始拷贝牌组为"战斗卡"，BattleCardState
     牌堆装副本 Id；改卡写副本；战斗结束副本随战斗态丢弃；永久升级
     才显式写回 master。作用域自动正确，"还原"动作根本不存在，与
     persistent/transient 划分严丝合缝。代价：副本↔master 映射管理。
  1b 战斗结束重置：直接写持久 CardInstance，结束时从 Definition 重建。
     硬伤：一旦出现"局内永久升级"，重置时必须区分永久/本场改动——
     等于被迫重新发明分层。不推荐。

────────────────────────────────────────────────────────────────────
方案 2：战斗层增量表（transient overlay）
────────────────────────────────────────────────────────────────────
原理：Definition/Instance 都不动，战斗态挂一张
      Dictionary<CardInstanceId, CardBattleDelta>；
      有效值 = Definition.Value + delta。
优点：
  - 作用域自动正确（表随 BattleState 丢弃）；纯数据好序列化（利回放）；
    无副本机制。
缺点：
  - 所有读数值处必须统一走 GetEffectiveValue() 查询函数，绕过即 bug；
    读路径多一次拼装。

────────────────────────────────────────────────────────────────────
方案 3：Hook 化（做成针对单卡的修改器）
────────────────────────────────────────────────────────────────────
原理："+2"注册为修改器，条件是"被改的卡 == A"，与力量/易伤同管道。
优点：
  - 全游戏只有一套数值管道，机制统一；不引入卡牌可变状态。
缺点：
  - 语义错位："卡的属性变了"被表达成"环境里挂了针对它的隐形 buff"。
  - 卡面 UI 想显示数字得跑整条链；链上堆满条件修改器后难以回答
    "这张卡现在到底是多少"；带条件的修改器比一个 int delta 难序列化。
  - Hook 适合"每次结算都要重新问"的事（力量会变、易伤会到期），
    不适合"改一次、之后一直如此"的事。

────────────────────────────────────────────────────────────────────
方案 4：分层数值（方案 1/2 的显式合成）
────────────────────────────────────────────────────────────────────
原理：有效基础值 = Definition.Value（永久模板）
                 + CardInstance.PermanentDelta（局内永久升级）
                 + BattleDelta（本场）；结算时再过修改器链。
优点：
  - "数值的生命周期"在类型上表达得最清楚，各种来源各有归宿。
缺点：
  - 前期结构最重；尚无升级/遗物系统时多数层是空的。

对比总览：

  方案          | 读路径   | 作用域还原 | 序列化 | 与STS2 | 推荐度
  --------------|----------|------------|--------|--------|--------
  1a 副本+实例  | 一次读取 | 自动(丢副本)| 好     | 一致   | 推荐
  1b 实例+重置  | 一次读取 | 手动重置   | 好     | 部分   | 不推荐
  2  增量表     | 查表拼装 | 自动(丢表) | 极好   | 不同   | 备选
  3  Hook 化    | 跑链推导 | 自动       | 中     | 错位   | 不推荐
  4  分层数值   | 多层求和 | 自动       | 好     | 近似   | 后期演进

------------------------------------------------------------------------

4. 结论
------------------------------------------------------------------------

已决策：采用【方案 1a：实例可变数值 + 战斗副本】。

理由修正（重要）：支撑方案 1 的不是性能。方案 2 多出的开销只是
查表加法，纳秒级、DBG 规模下不可测；且无论选哪个方案，重放 N 次时
力量/易伤的修改器链都必须跑 N 次（第 3 刀时力量可能已变，正确性
要求）。真正的理由是【语义】：卡的伤害应是一次读取即得的事实，
单一事实来源，UI 直读，调试直观。

实现要点：
  - 战斗开始时拷贝战斗卡副本，必须拷贝 CardEffect[] 数组本身，
    不能共享 Definition 的数组引用——否则"+2"写进所有同名卡共享的
    模板（此类设计最经典的 bug）。CardEffect 是 struct，数组拷贝后
    天然值独立。
  - 改卡（写副本）与改结算（修改器链）两条管道严格分离。
  - 数据流（修正《260612-report-combat-actor-state-modeling》讨论中
    "直接查 Definition"的描述）：
      战斗开始: CardInstance(master) ──拷贝──▶ 战斗卡副本(transient)
      打出卡:   副本.Effects[i].Value(基础值) ──▶ 修改器链 ──▶ 写目标
      "A卡+2":  写副本.Effects[i].Value，一次写入后所有读取自动正确
      战斗结束: 副本丢弃；永久升级显式写 master

待定实现细节（写代码时再定）：战斗副本的 Id 策略——发新
CardInstanceId 并维护副本→master 映射（更显式），或沿用 master Id
但放战斗专属容器（少一张表）。结合"战利品升级手牌"这类跨层操作
在 BattleCardPileSystem 动工时选择。

若未来出现局内永久升级与更多数值来源，可平滑演进为方案 4（分层），
副本机制不变，仅在 master 上加 PermanentDelta 层。
