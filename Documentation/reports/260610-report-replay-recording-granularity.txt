========================================================================
  报告：游戏录制/回放系统——录制粒度方案对比
  生成日期：2026-06-10
========================================================================

1. 背景与引言
------------------------------------------------------------------------

游戏录制/回放（Replay）系统的核心问题是：**录什么？**

录制的粒度决定了文件大小、实现复杂度、回放精度、以及对游戏架构
的侵入程度。不同类型的游戏选择了截然不同的方案。

本报告分析所有可行的录制粒度方案，并结合 Dota 2、StarCraft II、
Slay the Spire、炉石传说、Chess.com 等成功商业游戏的实际做法，
为本项目（DBG）提供选型参考。

------------------------------------------------------------------------

2. 代码分析与领域特征
------------------------------------------------------------------------

2.1 DBG 的领域特征（影响方案选择的关键因素）

  a) 确定性（Determinism）
     DBG 的游戏逻辑是离散的、回合制的。
     给定相同的初始状态 + 相同的玩家决策 + 相同的随机种子，
     结果完全一致。这是最适合"输入回放"的游戏类型。

  b) 输入频率极低
     一个回合中玩家的操作只有几次：打出卡牌、选择目标、结束回合。
     对比 Dota 2 每秒 30 个 tick，DBG 一局可能只有 50-200 次输入。

  c) 状态空间有限
     牌堆、手牌、HP、能量、Power 列表——所有状态可以用几 KB 描述。
     对比 3D 游戏需要记录每个实体的位置/旋转/速度。

  d) 随机性集中在少数节点
     洗牌、抽牌、随机生成卡牌——随机事件少且明确。
     只需一个种子即可复现所有随机结果。

2.2 本项目相关代码

  来源：Assets/Scripts/tools/Random.cs
  当前状态：空类，随机种子系统尚未实现。
  这意味着无论选择哪种方案，都需要先实现确定性随机数系统。

  来源：Assets/Scripts/gameStates/GameState.cs
  GameState 是集中式状态容器，包含所有游戏状态。
  这为"状态快照"方案提供了天然支持。

------------------------------------------------------------------------

3. 录制粒度方案一览
------------------------------------------------------------------------

方案 A：玩家输入层录制（Input-Level Recording）
======================================================================

原理：
  只录制玩家做了什么决策，回放时用相同的输入从头跑一遍游戏逻辑。

录制内容：
  {
      seed: 12345,                          // 随机种子
      initialDeck: ["Strike", "Strike", "Defend", ...],
      actions: [
          { turn: 1, type: "PlayCard", handIndex: 2, targetId: 3 },
          { turn: 1, type: "PlayCard", handIndex: 0, targetId: 3 },
          { turn: 1, type: "EndTurn" },
          { turn: 2, type: "PlayCard", handIndex: 1, targetId: 3 },
          { turn: 2, type: "SelectCard", pileType: "Discard", cardIndex: 0 },
          { turn: 2, type: "EndTurn" },
      ]
  }

回放时：
  1. 用 seed 初始化随机数生成器
  2. 加载 initialDeck
  3. 按顺序注入每个 action，游戏逻辑照常执行
  4. 所有中间状态自动产生（抽牌、伤害计算、Power 触发等）

文件大小估算（一局 DBG）：
  ~200 次操作 x ~20 字节/操作 = ~4 KB

优点：
  - 文件极小（KB 级别）
  - 实现简单，不需要修改游戏逻辑
  - 自然兼容所有 Action 类型（包括 CustomExecute）
  - 回放精度 100%（因为是重新执行完整逻辑）
  - 随游戏版本更新只需保证输入语义不变

缺点：
  - 必须保证游戏逻辑完全确定性（Deterministic）
    - 随机数必须用种子控制
    - 浮点运算必须一致（跨平台可能不同）
    - 不能依赖 Dictionary 遍历顺序等非确定性行为
  - 无法快进到任意时间点（必须从头跑到那一步）
    - 解法：定期存检查点快照
  - 游戏版本更新可能破坏旧录像
    - 如果修改了伤害公式或 Power 逻辑，旧录像回放结果会不同
  - 回放速度受限于游戏逻辑执行速度
    - 快进时需要跳过动画但仍执行逻辑

确定性要求清单（DBG 场景）：
  [必须] 随机数用种子控制（洗牌、抽牌、随机生成）
  [必须] 所有集合遍历顺序确定（用 List 不用 HashSet 做游戏逻辑）
  [不需要] 浮点一致性（DBG 用整数计算伤害/防御，无浮点问题）
  [不需要] 帧率无关（回合制，无物理模拟）

对于 DBG，确定性非常容易保证。


方案 B：Action 层录制（Action-Level Recording）
======================================================================

原理：
  录制游戏逻辑产生的每个 Action，回放时直接执行 Action 序列，
  跳过"从输入推导 Action"的过程。

录制内容：
  {
      actions: [
          { type: "ShuffleDeck", seed: 12345 },
          { type: "DrawCards", count: 5 },
          { type: "DealDamage", targetId: 3, amount: 8, sourceCardId: "Strike" },
          { type: "GainBlock", targetId: 0, amount: 5 },
          { type: "ApplyPower", targetId: 3, powerType: "Vulnerable", amount: 2 },
          { type: "DrawCards", count: 3 },
          { type: "DiscardCard", cardInstanceId: 42 },
          ...
      ]
  }

回放时：
  1. 按顺序取出 Action
  2. 直接执行每个 Action 的效果（不经过卡牌逻辑）
  3. UI 根据 Action 播放对应动画

文件大小估算（一局 DBG）：
  一次打牌可能产生 5-15 个 Action（扣费、移牌、伤害、触发Power等）
  ~200 次操作 x ~10 Action/操作 x ~30 字节/Action = ~60 KB

优点：
  - 不需要游戏逻辑完全确定性
    - 随机结果已经包含在 Action 数据中
  - 可以快进到任意位置（Action 是独立的状态变更）
  - 游戏逻辑更新不影响旧录像（Action 是结果，不是过程）
  - 回放速度不受限于游戏逻辑

缺点：
  - 文件较大（比方案 A 大 10-15 倍）
  - 所有 Action 必须可序列化
    - CustomExecute（Func/委托）无法直接序列化
    - 需要给每个 Custom Action 分配字符串 ID
  - 架构侵入性强：每个 Action 需要实现序列化/反序列化接口
  - 必须维护 Action 的向后兼容性
    - 新版本如果修改了 Action 的字段结构，旧录像解析失败
  - 需要一个"回放模式"的 ActionExecutor，跳过逻辑只执行状态变更

CustomExecute 序列化问题的解法：

  // 方法 1：注册表
  public static class CustomActionRegistry
  {
      private static Dictionary<string, Func<ActionContext, IEnumerator>> _registry
          = new Dictionary<string, Func<ActionContext, IEnumerator>>();

      public static void Register(string id, Func<ActionContext, IEnumerator> logic)
      {
          _registry[id] = logic;
      }

      public static Func<ActionContext, IEnumerator> Get(string id)
      {
          return _registry[id];
      }
  }

  // 录制时存: { type: "Custom", customId: "FiendFire", params: {...} }
  // 回放时: CustomActionRegistry.Get("FiendFire") 找到逻辑重新绑定

  // 方法 2：将 Custom Action 的执行结果展开为基础 Action 序列
  // FiendFire 执行后产生的实际 Action：
  //   ExhaustCard(card1), ExhaustCard(card2), ..., DealDamage(target, 7, hitCount=3)
  // 录制展开后的序列，回放时不需要再跑 FiendFire 的逻辑


方案 C：状态快照录制（State Snapshot Recording）
======================================================================

原理：
  定期（如每回合或每次操作后）保存完整的游戏状态快照。
  回放时直接加载快照，在快照之间插值/过渡。

录制内容：
  {
      snapshots: [
          {
              turnNumber: 1,
              phase: "PlayerTurn",
              timestamp: 0,
              state: {
                  playerHp: 72,
                  playerEnergy: 3,
                  playerBlock: 0,
                  powers: [{ type: "Strength", amount: 2 }],
                  drawPile: [cardId1, cardId2, ...],
                  hand: [cardId5, cardId6, cardId7, cardId8, cardId9],
                  discardPile: [],
                  enemies: [
                      { id: 3, hp: 45, block: 0, powers: [], intent: "Attack:12" }
                  ]
              }
          },
          {
              turnNumber: 1,
              phase: "AfterPlayCard",
              timestamp: 1,
              state: { ... }  // 打出一张牌后的完整状态
          },
          ...
      ]
  }

回放时：
  1. 按顺序加载快照
  2. 比较前后快照的差异，推断发生了什么
  3. 播放对应动画/过渡效果

文件大小估算（一局 DBG）：
  一局约 50-100 个快照 x ~500 字节/快照 = ~25-50 KB

优点：
  - 完全不依赖确定性
  - 可以跳转到任意时间点（直接加载对应快照）
  - 对游戏逻辑零侵入——只需要状态可序列化
  - 向后兼容性好（只要状态结构不变）
  - 调试价值极高——每个快照都是完整的游戏状态

缺点：
  - 文件最大（虽然 DBG 的状态小，所以实际还好）
  - 无法精确回放动画（快照之间的过渡是推断的，不是原始的）
  - 需要实现"状态差异推断"逻辑
    - 快照 A 手牌有 5 张，快照 B 手牌有 4 张少了 Strike
      -> 推断：打出了 Strike
    - 但某些情况难以推断（如牌被消耗 vs 被弃置 vs 被移到牌顶）
  - 无法回放玩家的操作意图（只看到结果，不知道玩家做了什么）
  - 复杂度随状态结构增长

优化：增量快照
  不存完整状态，只存与上一帧的差异（Delta）：
  { turn: 1, delta: { playerHp: -12, hand: { removed: [cardId5] }, ... } }
  可以大幅减小文件体积，但增加了回放实现复杂度。


方案 D：混合录制（Input + 检查点快照）
======================================================================

原理：
  以玩家输入录制为主（方案 A），每隔 N 个回合存一个状态快照（方案 C）。
  快进时加载最近的快照，再从该点开始重放剩余输入。

录制内容：
  {
      seed: 12345,
      initialDeck: [...],
      actions: [
          { turn: 1, type: "PlayCard", handIndex: 2, targetId: 3 },
          { turn: 1, type: "EndTurn" },
          ...
      ],
      checkpoints: [
          { afterTurn: 5, state: { ... } },
          { afterTurn: 10, state: { ... } },
          ...
      ]
  }

回放时：
  - 从头播放：用 seed + actions，和方案 A 一样
  - 跳到第 8 回合：加载 afterTurn:5 的检查点，
    然后从第 6 回合的 actions 开始重放

文件大小估算：
  输入数据 ~4 KB + 每 5 回合一个快照 x ~500 字节 x ~6 个 = ~7 KB

优点：
  - 兼具方案 A 的小体积和方案 C 的快进能力
  - 确定性验证：回放到检查点后与快照对比，可以检测不确定性 bug
  - 快进速度有保证（最多只需重放 N 个回合的逻辑）

缺点：
  - 实现复杂度最高（同时实现输入录制 + 快照 + 快照加载）
  - 仍需要确定性保证（检查点之间靠输入重放）
  - 检查点频率的选择需要权衡（频繁=文件大，稀疏=快进慢）

适用场景：需要快进功能的输入录制方案。


方案 E：视频录制（Screen Recording）
======================================================================

原理：
  直接录制游戏画面的视频流。与游戏逻辑完全解耦。

实现方式：
  - 系统级：Windows Game Bar、OBS、NVIDIA ShadowPlay
  - 引擎级：Unity Recorder 插件
  - 游戏内：逐帧捕获 RenderTexture 写入视频文件

文件大小估算：
  720p 30fps 10分钟 = ~200-500 MB（压缩后）

优点：
  - 与游戏逻辑完全解耦，零侵入
  - 100% 视觉还原
  - 不需要确定性
  - 不受版本更新影响

缺点：
  - 文件巨大（MB-GB 级别）
  - 无法交互（不能改视角、不能看对手手牌）
  - 无法提取游戏数据（不能做数据分析）
  - 不能用于断线重连或网络同步
  - 对于 2D 回合制 DBG，过度杀伤

适用场景：直播/内容创作，不适合作为游戏内 Replay 系统。

4. 商业游戏案例分析
------------------------------------------------------------------------

4.1 Dota 2 —— 方案 D（输入 + 检查点快照）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

录制粒度：服务器 Tick 级别的输入 + 定期快照

Dota 2 使用 Source 2 引擎，采用 Server-Authoritative 架构：
  - 服务器以 30 tick/秒 运行游戏模拟
  - 每个 tick 记录所有玩家的输入命令（移动、释放技能、购买物品等）
  - Replay 文件（.dem）包含：
    - 完整的初始状态
    - 每个 tick 的玩家输入 + 服务器事件
    - 定期的全量状态快照（约每 2-3 秒一次，称为 "full update"）

回放特性：
  - 可以快进/快退（通过快照跳转）
  - 可以自由切换视角（观察任意玩家/自由视角）
  - 可以查看双方完整信息（包括战争迷雾内的单位）
  - 支持慢放和暂停

文件大小：一局 40 分钟约 70-120 MB

为什么选这个方案：
  - Dota 2 是实时游戏，30 tick/秒，输入量大
  - 纯输入回放太慢（从头模拟 40 分钟太久），需要快照支持快进
  - 服务器权威，所有逻辑在服务器确定性执行
  - 需要支持观战者的自由视角


4.2 StarCraft II / StarCraft: Remastered —— 方案 A（纯输入录制）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

录制粒度：玩家输入命令

StarCraft 系列的 Replay 文件只存储：
  - 随机种子
  - 地图信息
  - 每个玩家在每个 game tick 的输入命令
    （选择单位、右键移动、建造建筑、使用技能等）

回放时完全重新模拟：
  - 加载地图 + 种子
  - 按 tick 注入玩家输入
  - 引擎从头跑一遍完整的游戏逻辑

文件大小：一局 20 分钟约 50-200 KB（极小）

为什么选这个方案：
  - RTS 引擎有严格的确定性保证（锁步同步 Lockstep）
  - 网络对战本身就要求确定性（两个客户端各自模拟，结果必须一致）
  - 文件极小，方便分享
  - 缺点是不能快进到任意位置（必须从头模拟）
    - SC2 通过加速模拟解决（跳过渲染，纯逻辑快进）

确定性保证措施：
  - 固定步长更新（fixed timestep）
  - 使用定点数（fixed-point arithmetic）代替浮点数
  - 禁止非确定性操作（如依赖系统时间、线程调度顺序）
  - 所有随机数通过种子生成


4.3 炉石传说（Hearthstone）—— 方案 B 变体（服务器事件流）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

录制粒度：服务器产生的游戏事件（类似 Action 层）

炉石传说采用服务器权威架构：
  - 所有游戏逻辑在服务器执行
  - 服务器向客户端发送事件流（PowerHistory）：
    - TAG_CHANGE entityId=3 tag=HEALTH value=25
    - BLOCK_START type=PLAY entity=Strike
    - TAG_CHANGE entityId=7 tag=DAMAGE value=6
    - BLOCK_END
    - TAG_CHANGE entityId=3 tag=ZONE zone=HAND -> PLAY
  - 客户端根据事件流更新 UI 和播放动画

这本质上是方案 B（Action 层），但更细粒度——每个状态变更都是一个事件。

炉石不提供官方 Replay 功能，但第三方工具（如 HSReplay.net）通过
截获 PowerHistory 日志实现了回放：
  - 录制：解析游戏日志中的 PowerHistory 事件
  - 回放：按顺序应用事件，重建游戏状态

文件大小：一局约 10-50 KB（纯文本日志）

为什么选这个方案：
  - 服务器权威，客户端不运行游戏逻辑，只接收事件
  - 事件流本身就是网络协议的一部分（不是专门为回放设计的）
  - 不需要确定性（服务器已经计算好了所有结果）
  - 天然支持观战（发送同样的事件流给观战者）


4.4 Slay the Spire 1 —— 无 Replay，使用种子系统
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

STS1 没有回放功能，但有一个相关系统：种子（Seed）。

  - 每局游戏有一个种子，决定所有随机事件
  - 玩家可以分享种子，其他人用相同种子开局
  - 但由于玩家决策不同，后续发展不同
  - 不是 Replay，而是"可复现的初始条件"

STS1 的存档系统：
  - 使用状态快照（方案 C）做存档/读档
  - 退出时保存完整游戏状态到 JSON
  - 重新打开时加载快照恢复

启示：对于单人 DBG，种子系统 + 存档可能比完整 Replay 更实用。


4.5 Chess.com / Lichess —— 方案 A 的极致简化
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

录制粒度：每一步棋的走法

国际象棋的"录像"就是棋谱：
  1. e4 e5
  2. Nf3 Nc6
  3. Bb5 a6
  ...

这是方案 A 的最纯粹形式：
  - 无随机性，不需要种子
  - 每步棋是一个确定性输入
  - 回放 = 按顺序执行每步棋
  - 文件极小（几百字节）
  - 支持跳转到任意步（因为每步棋都可以独立应用到棋盘状态）

PGN（Portable Game Notation）格式存在了几十年，向后兼容性极好。

启示：DBG 和国际象棋一样是离散回合制、输入频率极低，
方案 A 天然适合。


4.6 格斗游戏（Street Fighter 6、GGST）—— 方案 A（输入录制 + 回滚）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

录制粒度：每帧的玩家输入

格斗游戏使用 GGPO 风格的回滚网络同步：
  - 每帧记录双方输入（方向 + 按键，约 2 字节/帧/玩家）
  - 游戏逻辑完全确定性
  - 回放 = 用记录的输入从头模拟

训练模式的"录制"功能：
  - 录制一段操作（如连招输入序列）
  - 回放时 CPU 按录制的输入操作角色

确定性保证：定点数、固定帧率、确定性物理。

文件大小：一局 3 分钟 60fps = 约 20 KB

5. 方案对比总览
------------------------------------------------------------------------

  方案              | 文件大小 | 快进  | 确定性要求 | 侵入性 | 版本兼容 | 实现难度
  ------------------|----------|-------|-----------|--------|----------|--------
  A 玩家输入        | ~4 KB    | 差*   | 必须      | 极低   | 中       | 低
  B Action层        | ~60 KB   | 好    | 不需要    | 高     | 差       | 中
  C 状态快照        | ~50 KB   | 极好  | 不需要    | 低     | 中       | 中
  D 输入+检查点     | ~7 KB    | 好    | 必须      | 低     | 中       | 高
  E 视频录制        | ~300 MB  | 好    | 不需要    | 无     | 好       | 低

  * 方案 A 可通过跳过动画加速模拟实现快进

商业游戏选型参考：

  游戏类型    | 代表作              | 方案    | 原因
  ------------|---------------------|---------|----------------------------------
  MOBA        | Dota 2              | D       | 实时游戏+需要快进+服务器权威
  RTS         | StarCraft II        | A       | 锁步同步天然确定性+文件小
  CCG(服务器) | 炉石传说            | B       | 服务器权威+事件流就是网络协议
  CCG(单机)   | STS1                | 无      | 不做回放，用种子+存档
  棋类        | Chess.com           | A       | 离散回合制+零随机+极简
  格斗        | Street Fighter 6    | A       | 回滚网络要求确定性+输入极简
  FPS         | CS2, Overwatch      | D       | 实时+需要快进+demo文件

------------------------------------------------------------------------

6. 结论
------------------------------------------------------------------------

对于本项目（DBG），推荐方案 A（玩家输入录制）。理由：

  1. DBG 是离散回合制，确定性极容易保证
     - 只需要种子控制随机数
     - 整数运算，无浮点一致性问题
     - 无物理模拟，无帧率依赖

  2. 输入频率极低，文件天然极小（~4 KB/局）

  3. 实现难度最低，架构侵入性最小
     - 不需要修改 Action 系统
     - 不需要所有 Action 可序列化
     - CustomExecute 的序列化问题完全消失

  4. DBG 不太需要快进功能
     - 一局通常 5-15 分钟
     - 如果需要，可以跳过动画加速模拟
     - 真需要时可以升级到方案 D（加检查点）

  5. 与 StarCraft 和国际象棋的成功实践一致

实现前提：
  - 实现确定性随机数系统（Random.cs 用种子）
  - 所有游戏逻辑中的随机操作使用统一的种子随机数
  - 集合遍历使用 List 而非 HashSet/Dictionary

如果未来需要网络同步（多人 co-op），方案 A 也天然兼容——
只要双方用相同种子 + 相同输入序列，结果一致（类似 RTS 锁步同步）。

如果未来需要服务器权威架构，可以升级到方案 B（类似炉石传说）。
