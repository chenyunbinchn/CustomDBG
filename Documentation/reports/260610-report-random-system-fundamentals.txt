2. 什么是 RNG
------------------------------------------------------------------------

RNG = Random Number Generator（随机数生成器）。

在游戏中，"随机"无处不在：
  - 洗牌：52 张牌的顺序
  - 怪物 AI：这回合是攻击还是防御？
  - 掉落奖励：给玩家 3 张卡牌中选 1 张，是哪 3 张？

但计算机本身是确定性的——给它相同的指令，它永远做相同的事。
计算机无法产生"真正的随机数"。

所以计算机用的是**伪随机数生成器**（Pseudo-Random Number Generator,
简称 PRNG）。"伪"的意思是：它看起来像随机的，但实际上是用一个
数学公式算出来的，给定相同的起点，产生完全相同的序列。

------------------------------------------------------------------------

3. 伪随机数的原理
------------------------------------------------------------------------

3.1 最简单的伪随机数生成器

一个极简的公式（线性同余法，LCG）：

  下一个数 = (当前数 * A + B) mod M

假设 A=5, B=3, M=16，从"当前数=7"开始：

  第1次: (7  * 5 + 3) mod 16 = 38 mod 16 = 6
  第2次: (6  * 5 + 3) mod 16 = 33 mod 16 = 1
  第3次: (1  * 5 + 3) mod 16 = 8  mod 16 = 8
  第4次: (8  * 5 + 3) mod 16 = 43 mod 16 = 11
  第5次: (11 * 5 + 3) mod 16 = 58 mod 16 = 10
  ...

序列：6, 1, 8, 11, 10, ...

看起来"没有规律"，但它其实是完全确定的——因为公式是固定的。
如果你再次从 7 开始算，得到的序列一模一样：6, 1, 8, 11, 10, ...

这个"起始数"就叫**种子（Seed）**。

3.2 种子（Seed）的含义

  种子 = 随机序列的起点。

  相同的种子 → 相同的序列 → 相同的游戏结果

这就是为什么 Slay the Spire 可以让你输入一个种子来复现一局游戏。
种子决定了这局所有的"随机"事件：洗牌顺序、怪物行为、奖励内容。

例子：
  种子 = 42 → 序列: 6, 1, 8, 11, 10, 3, 15, ...
  种子 = 99 → 序列: 2, 13, 5, 0, 7, 12, 9, ...

不同的种子 → 不同的序列 → 不同的游戏体验。
相同的种子 → 完全相同的序列 → 完全相同的游戏。

3.3 System.Random 的使用

C# 提供了内置的伪随机数生成器：System.Random。

  System.Random rng = new System.Random(42);  // 种子 = 42

  rng.Next(10);   // 返回 0~9 之间的整数
  rng.Next(10);   // 返回下一个 0~9 之间的整数
  rng.Next(10);   // 返回再下一个...

如果你创建两个 System.Random(42)，调用相同次数的 Next，
结果完全一致：

  System.Random rng1 = new System.Random(42);
  System.Random rng2 = new System.Random(42);

  rng1.Next(10) == rng2.Next(10)   // true，永远相等
  rng1.Next(10) == rng2.Next(10)   // true，永远相等
  rng1.Next(10) == rng2.Next(10)   // true，永远相等

这就是确定性的本质。STS2 的 Rng 类底层就是 System.Random。

3.4 Counter（计数器）的含义

每调用一次 Next，随机数生成器内部就"前进一步"。
Counter 记录的就是"前进了几步"。

  Rng rng = new Rng(seed: 42);  // Counter = 0

  rng.NextInt(10);  // Counter = 1，返回 6
  rng.NextInt(10);  // Counter = 2，返回 1
  rng.NextInt(10);  // Counter = 3，返回 8

为什么需要 Counter？

  **Counter 是为存档/读档服务的，不是为 Replay 服务的。**

  两者的区别：

  存档/读档：
    保存"某一时刻的照片"。玩家在第 3 回合存档退出，
    需要保存当前所有游戏状态（HP、手牌、牌堆等），
    以及每个 Rng 流的 Counter。

    存档内容：{ seed: 42, shuffleCounter: 7, aiCounter: 3, ... + 游戏状态 }

    读档时：用 seed 创建 Rng，快进 Counter 步恢复内部状态，
    再加载游戏状态快照。这样后续的随机数序列和存档前完全一致。

    如果不保存 Counter，读档后 Rng 从 0 开始，
    后续洗牌结果全部错乱。

  Replay（回放）：
    保存"从头到尾的操作录像"。录制的内容是种子 + 玩家输入序列：
    { seed: 42, inputs: [打出手牌2, 结束回合, 打出手牌0, ...] }

    回放时从头重跑整个游戏：用 seed 初始化 Rng（Counter=0），
    按顺序注入玩家输入，游戏逻辑完整执行一遍。
    Rng 的 Counter 自然地从 0 增长，不需要手动设置。

    Replay 不需要 Counter，因为它不跳到中间某一步，
    而是从头完整地重放整个过程。玩家的输入驱动游戏推进，
    种子保证所有随机结果一致。

  总结对比：
    存档/读档 = 跳到照片那一刻 → 需要 Counter 恢复 Rng 状态
    Replay    = 从头放录像     → 不需要 Counter，种子+输入足够

4. 哈希与确定性哈希
------------------------------------------------------------------------

4.1 什么是哈希

哈希（Hash）= 把任意数据变成一个固定长度的数字。

  hash("hello")  → 1234567
  hash("world")  → 8901234
  hash("hello")  → 1234567   （相同输入 → 相同输出）

哈希的特点：
  - 相同输入 → 永远相同输出
  - 不同输入 → 通常不同输出（偶尔可能碰撞，但概率极低）
  - 单向的——知道 1234567 无法反推出 "hello"
  - 输出看起来"没有规律"——"hello" 和 "hellp" 的哈希值差异很大

4.2 哈希在本项目中的用途

我们需要哈希来做一件事：**从一个主种子派生多个子种子**。

  主种子: 42
  洗牌种子: hash("42" + "shuffle")    → 729105
  怪物AI种子: hash("42" + "monster_ai") → 384712

这样一个主种子就能产生多个互不相关的随机流。

4.3 为什么 string.GetHashCode() 不能用

C# 自带的 string.GetHashCode() 是一个哈希函数，但它有一个致命问题：

  **不保证跨进程/跨平台一致。**

.NET Core 为了安全性，每次启动程序时会用不同的随机种子初始化
GetHashCode 的内部状态。所以：

  // 第一次运行程序
  "hello".GetHashCode()  → 1234567

  // 关闭程序，重新运行
  "hello".GetHashCode()  → 9876543   // 不一样了！

这对游戏来说是灾难性的：
  - 第一次运行：hash("42shuffle") = 729105 → 洗牌结果 A
  - 重启游戏：hash("42shuffle") = 382910 → 洗牌结果 B
  - 同一个种子，两次运行结果不同！Replay 和存档全部失效。

4.4 确定性哈希

**确定性哈希 = 不管在哪里运行、运行多少次，相同输入永远得到相同输出。**

自己写一个简单的哈希函数就能保证：

  public static int DeterministicHash(string str)
  {
      int hash1 = 352654597;
      int hash2 = hash1;
      for (int i = 0; i < str.Length; i += 2)
      {
          hash1 = ((hash1 << 5) + hash1) ^ str[i];
          if (i == str.Length - 1) break;
          hash2 = ((hash2 << 5) + hash2) ^ str[i + 1];
      }
      return hash1 + hash2 * 1566083941;
  }

这段代码没有任何外部依赖、没有随机化、纯数学运算。
不管在 Windows、Mac、Linux，不管运行几次：

  DeterministicHash("hello") → 永远是同一个数字

STS2 用的就是这个算法（来自 .NET Framework 的旧版 GetHashCode 实现）。

让我逐行解释这个算法：

  int hash1 = 352654597;      // 初始值，一个随意选的大质数
  int hash2 = hash1;          // 第二个哈希值，用于混合

  for (int i = 0; i < str.Length; i += 2)   // 每次处理两个字符
  {
      // 处理第一个字符
      hash1 = ((hash1 << 5) + hash1) ^ str[i];
      // hash1 << 5 = hash1 * 32
      // (hash1 << 5) + hash1 = hash1 * 33
      // 然后和字符的 ASCII 值做异或（XOR）
      // 效果：把字符的信息"混入"hash1

      if (i == str.Length - 1) break;  // 奇数长度字符串的最后一个

      // 处理第二个字符，混入 hash2
      hash2 = ((hash2 << 5) + hash2) ^ str[i + 1];
  }

  return hash1 + hash2 * 1566083941;
  // 最后把两个哈希值合并
  // 1566083941 也是一个大质数，用于减少碰撞

为什么用两个哈希值交替处理？
  → 减少碰撞概率。如果只用一个累加器，
    "ab" 和 "ba" 更容易产生相同的哈希值。
    两个交替处理，混合效果更好。

为什么用 hash * 33 + XOR？
  → 这是经典的 DJB2 哈希算法的变体，
    被证明对字符串有很好的分散性。
    33 这个乘数在实践中碰撞率很低。

5. 子种子派生的原理
------------------------------------------------------------------------

5.1 问题：一个种子不够用

假设整局游戏只用一个种子 42，所有随机操作共用一个序列：

  Rng rng = new Rng(42);
  序列: 6, 1, 8, 11, 10, 3, 15, 4, 9, 2, ...

  洗牌用了前 3 个数: 6, 1, 8
  怪物 AI 用了第 4 个数: 11
  洗牌又用了第 5 个数: 10
  ...

问题来了：如果下个版本你加了一种新的怪物技能，怪物 AI 多消耗了
1 个随机数，那么从那一刻开始，洗牌拿到的数就全变了。

  旧版本: 洗牌拿到 6,1,8 → AI拿到 11 → 洗牌拿到 10
  新版本: 洗牌拿到 6,1,8 → AI拿到 11,3 → 洗牌拿到 15（变了！）

一个系统的改动连锁影响了其他所有系统。

5.2 解法：每个系统独立的种子

  主种子 42
    → 洗牌种子 = DeterministicHash("42" + "shuffle")    = 729105
    → AI种子   = DeterministicHash("42" + "monster_ai")  = 384712

  Rng shuffleRng = new Rng(729105);    // 独立序列
  Rng aiRng      = new Rng(384712);    // 独立序列

现在洗牌和 AI 各有自己的序列，互不干扰。
AI 多消耗几个随机数，洗牌的结果完全不变。

5.3 为什么用哈希来派生

为什么不直接用 seed+1, seed+2, seed+3？

  洗牌种子 = 42
  AI种子   = 43
  奖励种子 = 44

这样做的问题：相邻的种子可能产生相似的序列开头。
System.Random(42) 和 System.Random(43) 的前几个输出可能有相关性。

哈希的作用是"打散"——42 和 43 只差 1，但 hash(42) 和 hash(43)
差了十万八千里，产生的序列完全不相关。

更准确地说：

  seed = 42
  hash("42shuffle")    = 729105    → 序列 A
  hash("42monster_ai") = 384712    → 序列 B

  seed = 43
  hash("43shuffle")    = 102938    → 序列 C（和 A 完全不同）
  hash("43monster_ai") = 851203    → 序列 D（和 B 完全不同）

哈希保证了：不管主种子多接近，派生出的子种子都是"远离"的。

6. 为什么需要 RngSet
------------------------------------------------------------------------

6.1 直接原因：隔离

上面已经解释了核心原因——隔离。再用一个具体的 DBG 场景说明：

  回合开始 → 抽 5 张牌（从洗好的牌堆中取前 5 张）
  玩家打出 Discovery（随机生成 3 张卡供选择）
  玩家选了一张，结束回合
  回合结束 → 怪物选择意图

  如果共用一个 Rng：
    抽牌消耗 0 次（牌堆已经洗好了，只是取前 5 张）
    Discovery 消耗 3 次（生成 3 张随机卡）
    怪物 AI 消耗 1 次

  如果玩家没有打出 Discovery 而是打出了 Strike：
    抽牌消耗 0 次
    Discovery 没消耗
    怪物 AI 消耗 1 次——但它是序列中的第 1 个数，
    上一种情况是第 4 个数。怪物行为因此不同。

  玩家的一个选择（打不打 Discovery）影响了怪物的行为。
  这不是 bug，但这样设计的话，Replay 和 Mod 容易出问题。

  如果用 RngSet（分流）：
    Discovery 用 CardGeneration 流
    怪物用 MonsterAi 流
    两个流互不干扰。打不打 Discovery 只影响 CardGeneration 流，
    怪物的行为不变。

6.2 实用原因：调试

Bug 报告："种子 12345 下，第 3 回合洗牌结果不对"。

如果只有一个流，你需要追踪整个游戏中所有系统的每一次随机调用，
才能定位问题。

如果有 RngSet，你只需要看 Shuffle 流的 Counter 是否正确。
其他流的调用完全无关。

6.3 需要几个流？

STS2 用了 15 个，但很多是细分优化。起步建议 3-4 个：

  Shuffle       — 洗牌专用
  MonsterAi     — 怪物意图选择
  CardGeneration — 随机生成卡牌（Discovery 等）
  General       — 其他杂项

原则：如果两个系统的随机调用次数可能因玩家决策而变化，
且你不希望它们互相影响，就分成两个流。

7. Fisher-Yates 洗牌算法
------------------------------------------------------------------------

7.1 问题：如何公平地洗一副牌？

"公平"的意思是：52 张牌的所有排列（52! 种）出现的概率相等。

7.2 错误的做法

  // 错误方法 1：每张牌随机和任意一张交换
  for (int i = 0; i < n; i++)
  {
      int j = rng.NextInt(n);    // 0 到 n-1 的随机位置
      Swap(list[i], list[j]);
  }

  这看起来合理，但分布不均匀。

  以 3 张牌 [A, B, C] 为例：
    可能的排列有 3! = 6 种：ABC, ACB, BAC, BCA, CAB, CBA
    上述算法有 n^n = 3^3 = 27 种等概率的执行路径
    27 不能被 6 整除 → 某些排列的概率必然比其他的高

  // 错误方法 2：每张牌分配一个随机数，然后排序
  // 可以工作，但效率低（O(n log n)），且排序的稳定性会引入偏差

7.3 正确的做法：Fisher-Yates 算法

  for (int i = n - 1; i > 0; i--)
  {
      int j = rng.NextInt(i + 1);   // 0 到 i（包含 i）的随机位置
      Swap(list[i], list[j]);
  }

  关键区别：j 的范围是 [0, i]，而不是 [0, n-1]。
  随着 i 递减，j 的范围越来越小。

  用 3 张牌 [A, B, C] 手动执行：

  初始: [A, B, C]

  i=2: j = rng.NextInt(3) → 可能是 0, 1, 或 2
    j=0: 交换 list[2] 和 list[0] → [C, B, A]
    j=1: 交换 list[2] 和 list[1] → [A, C, B]
    j=2: 交换 list[2] 和 list[2] → [A, B, C]（不变）

  i=1: j = rng.NextInt(2) → 可能是 0 或 1
    j=0: 交换 list[1] 和 list[0]
    j=1: 不变

  i=0: 循环结束

  执行路径数 = 3 * 2 * 1 = 6，恰好等于 3! = 6 种排列。
  每种排列恰好对应一条路径 → 完全均匀分布。

7.4 为什么 Fisher-Yates 是正确的

  数学证明的直觉：

  第 1 步（i=n-1）：从 n 个元素中随机选 1 个放到最后一个位置。
    → 每个元素被选中的概率 = 1/n ✓

  第 2 步（i=n-2）：从剩下 n-1 个元素中随机选 1 个放到倒数第二个位置。
    → 每个剩余元素被选中的概率 = 1/(n-1)
    → 某个元素在倒数第二位的总概率 = (n-1)/n * 1/(n-1) = 1/n ✓
      （第一步没被选中的概率 * 第二步被选中的概率）

  第 k 步：同理，每个元素出现在任意位置的概率都是 1/n。

  所以 Fisher-Yates 是**唯一在 O(n) 时间内实现均匀随机排列**的算法。

7.5 在代码中的样子

  public static void Shuffle<T>(this List<T> list, Rng rng)
  {
      int n = list.Count;
      while (n > 1)
      {
          n--;
          int k = rng.NextInt(n + 1);   // [0, n]
          T temp = list[n];
          list[n] = list[k];
          list[k] = temp;
      }
  }

  注意：这里是 while 循环版本，和 for 循环等价：
    n-- 先执行，所以 n 从 Count-1 开始递减到 1。
    rng.NextInt(n + 1) 的范围是 [0, n]，
    和 for 版本的 rng.NextInt(i + 1) 完全一致。

7.6 确定性保证

  List<string> deck = new List<string> { "Strike", "Defend", "Bash", "Anger" };

  // 第一次
  Rng rng1 = new Rng(seed: 42);
  deck.Shuffle(rng1);
  // 结果: ["Bash", "Strike", "Anger", "Defend"]（举例）

  // 第二次，相同种子
  deck = new List<string> { "Strike", "Defend", "Bash", "Anger" };
  Rng rng2 = new Rng(seed: 42);
  deck.Shuffle(rng2);
  // 结果: ["Bash", "Strike", "Anger", "Defend"]（完全一样）

  因为 rng1 和 rng2 的种子相同，NextInt 的返回序列完全相同，
  Fisher-Yates 的交换过程完全相同，最终结果完全相同。

  这就是"确定性洗牌"——Replay 系统的基石。

8. 完整知识链总结
------------------------------------------------------------------------

把所有概念串起来：

  [真随机不存在于计算机]
      ↓
  [伪随机数生成器（PRNG）]
  = 一个数学公式，给定起点，产生看似随机的序列
      ↓
  [种子（Seed）]
  = PRNG 的起点。相同种子 → 相同序列 → 相同结果
      ↓
  [Counter（计数器）]
  = 记录 PRNG "前进了几步"。用于存档/读档时恢复 Rng 状态。
    注意：Replay 不需要 Counter（从头重跑，Counter 自然产生）
      ↓
  [确定性哈希]
  = 把任意数据变成固定数字的函数。
    保证：相同输入 → 永远相同输出（跨平台、跨进程）
    用途：从主种子派生子种子
      ↓
  [子种子派生]
  = 用确定性哈希把"主种子 + 流名称"变成新的种子
    hash("42" + "shuffle") → 729105
    保证不同流的种子"远离"，序列不相关
      ↓
  [RngSet（多流管理）]
  = 为每个系统维护独立的 Rng 实例
    洗牌流、AI 流、卡牌生成流各自独立
    一个系统的随机消耗不影响其他系统
      ↓
  [Fisher-Yates 洗牌]
  = 唯一正确的 O(n) 均匀洗牌算法
    配合确定性 Rng → 相同种子永远产生相同的洗牌结果
      ↓
  [游戏确定性]
  = 相同种子 + 相同玩家输入 → 完全相同的游戏过程
    这就是 Replay 方案 A 的基础

9. 结论
------------------------------------------------------------------------

随机数系统的本质是一个悖论：
**用完全确定的方法，产生看起来不确定的结果。**

对于 DBG 项目，需要实现的核心组件：

  1. Rng 类：封装 System.Random + 种子 + 计数器
  2. SeedHelper：确定性哈希函数 + 子种子派生
  3. RngSet：管理多个独立随机流
  4. Shuffle 扩展方法：Fisher-Yates 算法

这四个组件加起来不超过 100 行代码，但它们是整个游戏确定性的基石：
没有它们，洗牌不可复现，存档不可恢复，Replay 不可实现。
