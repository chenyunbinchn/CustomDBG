1. 背景与引言
------------------------------------------------------------------------

  「钩子（Hook）」指在战斗生命周期节点（抽牌前后、出牌后、回合结束、
  战斗开始）对外广播的触发点，供横切实体（遗物 / Power / 道具）订阅并
  做出反应。本报告只讨论这种【事件钩子】，它与【修改器链】是两套不同
  机制（见 2.4），后者见《260609-report-modifier-chain》。

  当前代码中事件钩子【尚无任何实现】，仅以 Todo 注释占位。本报告先以
  实代码确认现状，再给候选设计——候选设计明确标注，不与现状混淆
  （依 CLAUDE.md 证据要求）。

      :13-16）。
    - 归属：GameState 持有 GameActionManager（GameState.cs:18）与
      ActionExecutor（:19），Init 注入 MonoBehaviour 宿主（:21-23）。
    - 反应可写的状态：EnemyInstance.Hp（EnemyInstance.cs:5）、
      BattleState.PlayerEnergies（BattleState.cs:11）。
    结论：乙C 的「反应入队」可直接复用此队列 + 执行器，无需另造管道。

  2.3 出牌钩子（甲3）的落点
    PlayCard 尚未实现（BattleSystem.cs:26-28 throw NotImplementedException）。
    候选的 PlayCardAction（见《260616-report-action-queue-granularity》
    方案 1）的 Execute() 内是「AfterPlayCard」钩子的自然触发点。

  2.4 与修改器链的区分（避免混淆，依 CLAUDE.md 消歧规则）
    - 事件钩子：回答「发生了某件事，谁要反应」，反应是副作用（乙C 中即
      入队新 Action）。触发于生命周期节点。
    - 修改器链：回答「某个值生效前如何被变换」，改的是一个数（伤害基础
      值 → +力量 → ×易伤 → 最终值），见《260609-report-modifier-chain》。
    两者可由同一遗物分别使用，但机制不同，不可把钩子写成「顺便改数值」。

3. 设计方案
------------------------------------------------------------------------

  钩子有两个正交决定：触发点放哪（甲），用什么机制（乙）。

  3.1 甲、触发点层级
    甲1 放 BattleSystem 生命周期点（现 Todo 位置）。
      优：与回合流程一一对应、遗物逻辑好定位。
      缺：只覆盖粗粒度节点，管不到「每个 Action 前后」。
    甲2 放 ActionExecutor，每个 Action 前后全局广播（BeforeAction /
        AfterAction，对应《260613-report-action-queue-and-executor》第 (j)
        节执行器级钩子）。
      优：任何 Action 可被监听、最通用。
      缺：粒度过细；监听器需自行判断 Action 类型，易把队列业务语义污染
      进监听器。
    甲3 放具体 Action 的 Execute()（如 PlayCardAction 内 AfterPlayCard）。
      优：钩子点与语义绑定最紧（订阅「出牌后」即字面意义）。
      缺：钩子点分散在各 Action，靠约定别漏。
    倾向：甲1（回合级）+ 甲3（卡牌级）组合；甲2 等真有细粒度横切需求再加。

  3.2 乙、反应机制
    乙A C# event / 多播委托（遗物 += handler）。
      优：写法最省。
      缺：调用顺序 = 订阅顺序，隐式且脆弱；两个遗物反应顺序不同会改变
      RandomManager 的随机消耗序列 → 回放发散（见
      《260610-report-replay-recording-granularity》）。对本项目强确定性
      架构是隐患。
    乙B 有序订阅表，触发时【同步直接做副作用】。
      优：顺序显式可控、可复现。
      缺：副作用绕过 Action 管道（无动画 / 无修改器链 / 无死亡级联），
      与正常出牌路径行为易不一致；非平凡反应会重复逻辑。
    乙C 有序订阅表 + 【反应入队为 Action】（复用执行器）。
      原理：监听器被触发时不直接改状态，而是 GameActionManager.Add 一个
      反应 GameAction，丢回执行器按 FIFO 跑。
      优：反应与卡牌效果共享同一条执行 / 动画 / 确定性管道，行为一致；
      反应里的随机也走正常 Action 执行序。
      缺：反应延迟到队列轮到它才发生（非同步立刻）；每种反应都需一个
      对应的 GameAction 类才能表达。
    注：乙C 复用乙B 的「有序订阅表」管道，二者接口相同，仅监听器体不同
    （改状态 vs 入队）；同一遗物可一条反应走 C、一条走 B，不冲突。

    对比：
      机制 | 走Action管道 | 与出牌一致 | 需新建Action | 确定性    | 适合
      -----|--------------|------------|--------------|-----------|------------------
      乙A  | -            | -          | -            | 差(隐式序)| 不推荐
      乙B  | 否           | 易不一致   | 否           | 靠Order   | 纯数据小反应
      乙C  | 是           | 一致       | 每种都要     | 靠Order   | 有动画/级联反应

4. 结论
------------------------------------------------------------------------

  推荐 甲1 + 甲3 + 乙C：
    - 触发点：回合级钩子在 BattleSystem（替换现 Todo），卡牌级钩子在
      PlayCardAction.Execute()。
    - 机制：有序 HookBus（按 Order 排序后遍历，杜绝 event 隐式乱序）+
      监听器反应入队为 GameAction，复用 ActionExecutor / 队列。
    - 乙B 仅留给一行即完、绝不触发后续的纯数据反应（如改能量 / 置标记）。

  最小验证（候选实现，未编译）：
    新增 EnumHookType / HookContext / IHookListener / HookBus（hooks/）+
    示例遗物 AfterPlayDealRelic（relics/，AfterPlayCard 时
    Add(new DamageAction().Create(2))）；GameState 持有 HookBus；在
    UnityBoostrap.Start 注册遗物 → HookBus.Fire(AfterPlayCard) →
    ActionExecutor.Kick 执行器。

  端到端验证前置（当前代码 bug，须先修）：
    - ActionExecutor.Kick 守卫条件反了（ActionExecutor.cs:20 为
      `if (!_isRunning) return;`，应为 `if (_isRunning) return;`），否则
      Run 永不启动、反应 Action 永不执行。
    - UnityBoostrap.cs:14 以 `GameState _gameState = new GameState()`
      遮蔽字段，字段恒为 null（Start 内冒烟测试用局部变量可跑，但属
      latent bug）。
    - 真实对局中 Kick 应在「入队之后」调用（如 BattleSystem 触发
      AfterPlayCard 后），非空 Update 轮询。

  交叉引用：
    - 执行器 / 队列与执行器级钩子（甲2）：《260613-report-action-queue-and-executor》（第 (j) 节）
    - 修改器链（另一类机制，2.4 区分）：《260609-report-modifier-chain》
    - 出牌粒度与 PlayCardAction（甲3 落点）：《260616-report-action-queue-granularity》
    - 确定性 / 回放对反应顺序的约束（乙A 风险）：《260610-report-replay-recording-granularity》

  本节补足正文缺失的一环：参考实现 STS2 的【实际】钩子实现（带文件

  5.1 调研范围与可信度
    源：D:\Decompiled Projects\Slay the Spire 2\src（Godot + C# 反编译）。
    仅读 Hook + 牌堆 + Power 相关约 10 个文件（src/Core 有 3393 个 .cs），
    系抽样而非全面审计。反编译会丢注释、生成 _003C_003E.. / InlineArray
    等编译器名，故本节只评架构 / 数据流，不评注释与局部命名。

  5.2 分发器：Hook 静态类（集中分发，79 个事件点）
    来源：src/Core/Hooks/Hook.cs:26（public static class Hook）
    79 个事件点，每个一个 static async Task，统一模板（:28-35 AfterActEntered）：
        foreach (AbstractModel model in combatState.IterateHookListeners())
        {
            await model.AfterCardPlayed(ctx, play);   // :181-197 带参版
            model.InvokeExecutionFinished();
        }
    即「战斗流程在节点显式调 Hook.Xxx → Hook 遍历监听者调其同名方法」。
    不是事件总线 / 订阅，是集中遍历分发。

  5.3 监听者契约：AbstractModel 虚方法（默认 no-op）
    来源：src/Core/Models/AbstractModel.cs:29（abstract 基类，~180 virtual）
      :236  public virtual Task AfterCardPlayed(...) => Task.CompletedTask;
      :121  InvokeExecutionFinished()（触发 :45 的 ExecutionFinished 事件）
    所有战斗对象（Power / Relic / Card / Monster / Potion / Orb…）共用此
    基类，每个事件一个默认空虚方法，子类只覆盖关心的。代价：上帝基类
    （1034 行、~180 virtual）。

  5.4 监听者收集：IterateHookListeners（即时收集 + 隐式订阅）★关键
    来源：src/Core/Combat/CombatState.cs:271-354
    每次事件【从零重建一个 list】，遍历收集（按序）：
      每个 creature：creature.Powers（状态）；怪物 → creature.Monster；
      玩家 → Relics(未 melted)、PotionSlots、OrbQueue.Orbs、
             所有牌堆每张 CardModel + 其 Affliction + Enchantment；
      全局：Modifiers、BadgeModels、MultiplayerScalingModel；
      收尾：if (Contains(item)) yield（过滤已移除者）+ ModHelper mod 扩展。
    要点：无订阅表、无 += / -=；【在场即监听】，每事件现取，故监听者
    集合恒与战场实况一致，且【遍历顺序固定 → 确定性】（印证本报告对乙A
    隐式乱序的否定、对确定顺序的要求）。代价：每事件 O(全部对象) 重建
    （STS2 用 Players.Count*50 预分配容量摊销）。

  5.5 监听者创建时机
    Power（combat 级，动态）：src/Core/Commands/PowerCmd.cs:33-55 Apply<T>：
      ModelDb.Power<T>() 取不可变模板 → FindExistingInstanceForStacking
      （可叠加则改量、不新建）→ 否则 powerModel.ToMutable() 克隆可变实例
      → 一串 Hook（BeforePowerAmountChanged / ModifyPowerAmount…）
      → creature.ApplyPowerInternal 加进容器。
    容器：src/Core/Entities/Creatures/Creature.cs:34 _powers、:276 Powers、
      :517-529 ApplyPowerInternal。
    层级（按容器归属推断，未逐一读各自创建点）：Relic = run 级拾取时；
      Monster / Card = 战斗开始。
    要点：【创建并放进它该在的权威容器，即自动成为监听者，无注册步骤】。

  5.6 反应与 action 队列的桥：GenericHookGameAction
    来源：src/Core/GameActions/GenericHookGameAction.cs:1-72
      class GenericHookGameAction : GameAction；RecordableToReplay => false；
      ChoiceContext（HookPlayerChoiceContext，处理 hook 内玩家选择）；
      多端用 HookActionEnqueuedMessage 同步。
    即 hook 触发的反应可作为 GameAction 入队 —— 直接印证本报告【乙C】。

  5.7 具体监听者示例
    来源：src/Core/Models/Powers/AfterimagePower.cs:1-48
      override BeforeCardPlayed：记录本次出牌时的层数；
      override AfterCardPlayed：await CreatureCmd.GainBlock(...)（产出效果）。
    即「子类覆盖两个 hook、在 After 里产出效果」的最小真实样例。

  5.8 与本报告方案的对照（印证 / 差异 / 补充）
    印证：
      - 乙C（反应入队为 Action）= STS2 GenericHookGameAction（5.6）。
      - 否定乙A（event 隐式序）= STS2 无 +=、靠固定遍历定序（5.4）。
      - 钩子点与语义绑定（甲3）= STS2 在流程节点显式调 Hook.Xxx。
    差异（机制）：
      - STS2 用 async / await；本项目用协程 yield。对应：async Task ↔
        IEnumerator、await ↔ yield return、Task.CompletedTask ↔ 立即结束
        的协程。故本项目走乙C 不必引入 async，反应 GameAction.Execute 用
        协程即可。
    补充（本节新增）★：
      - 本报告 3.2 乙B / 乙C 假设「有序订阅表 + 注册 / 注销」。STS2 给出
        更优变体：【免注册、即时收集】——不维护订阅表，改为
        BattleState.IterateHookListeners() 每次从权威容器（EnemyList 各
        敌人的状态、玩家遗物列表）现取，顺序由容器遍历固定。既省去
        注册 / 注销维护，又天然确定、无「忘记注销的幽灵监听者」。建议
        本项目采纳此变体替代显式订阅表。
    规模警示：
      - STS2 的 79 个事件点是数百 Power / Relic 内容【堆出来的果，非设计
        的因】（src/Core/Models/Powers 有 261 个 .cs）。本项目应按内容需求
        增量加，起步只做最小通知类集（OnPlayerTurnStart / End、
        AfterCardPlayed、Before / AfterDrawCard 约 4–6 个）。
      - STS2 的 AfterModifying* 系列是【修改类】钩子（改伤害 / 抽牌数等），
        对应本项目【修改器链】，按 2.4 与本类事件钩子分离，见
        《260609-report-modifier-chain》，勿混入本系统。

  5.9 对结论的补充
    维持正文 4 的推荐（甲1 + 甲3 + 乙C），并据本节补一条：监听者收集
    采用 STS2 式【即时从权威容器收集】，替代 3.2 的显式订阅表 / 注册——
    前提是先建好监听者容器（EnemyList 各敌人的状态集合、玩家遗物列表）；
    当前 EnemyInstance 仍为空壳，须先补。

  5.10 广播 + 自过滤的权衡（监听者侧样板，及减负建议）
    现象：IterateHookListeners（5.4）收集【全场】监听者，Hook 把事件
    【无差别广播】给每一个 → 任一张牌打出时，场上每个监听者（含敌方
    身上的同名 Power）的对应 hook 都会被调到。
    证据：src/Core/Models/Powers/AfterimagePower.cs 两个 hook 开头都先
      `if (cardPlay.Card.Owner.Creature != base.Owner) return;`——监听者
      自己判「这张牌是不是我主人打的」，不是则早退。
    权衡：分发端极简（无差别广播、无按 owner 分桶的订阅管理），代价是
    把【相关性过滤】责任下放到每个监听者，每个 hook 方法都要重复写
    `== Owner` / target 判定这类样板。事件总线若按 owner 分桶订阅可省掉
    自判，但订阅 / 注销管理更复杂（且与 5.4「免注册即时收集」相悖）。
    对本项目：若采纳 5.4 的即时收集 + 集中广播，监听者（遗物 / 状态）的
    hook 同样要自过滤。建议在 HookContext 里带上【事件源 / owner】
    （出牌者 / 伤害来源等），并给 IHookListener 一个基类 helper（如
    bool IsSelf(HookContext ctx) => ctx.Source == Owner;），把「与我相关
    吗」收敛成一行，减少每个监听者的重复样板。
